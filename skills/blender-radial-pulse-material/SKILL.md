# 世界空间「径向距离场」程序化发光材质 + 空物体属性驱动

> 一句话：把图案写成**只依赖到共享中心的距离 r（和方向 d）**的函数，
> 那么「从中心向外发散」是几何必然、不是技巧；多个共心物体共享同一个 3D 场，交线自动连续。

**两个前置 skill，先读：**

| 需要什么 | 去哪 |
|---|---|
| 怎么把代码送进正在运行的 Blender（桥、客户端封装、120s 上限、5.x Slotted Action、引用/删除写法） | **`blender-bridge-ops`** |
| 世界空间程序化材质的**通用机制**：SINGLE_PROP 驱动、tag 矩阵、读驱动真值必须走求值依赖图、隔离场景渲预览、像素级验收、ColorRamp 类对比度 | **`blender-procedural-emission-material`** |
| **建成之后的维护**：查"这个参数到底谁在读"（引用体检）、关键帧动画收敛成常量、参数改名 / 驱动换轴而不留失效驱动 | **`blender-driver-param-maintenance`** |

**本 skill 只讲径向这一路独有的东西**：距离场怎么建、环形掩码怎么做、以及「循环脉冲」的时间轴。

**实测环境**：Blender **5.2.0 LTS** / EEVEE Next / Windows。

## 铁律

1. **先只读侦察**：对象世界包围盒、中心在哪、现有材质/节点/驱动。**"共心"这种描述必须量出来验证**，别信描述
2. **先建干跑副本再做实验**：要验证 API 行为，用**临时对象/材质**试，试完删净并断言无残留
3. **改动前放还原点**（`blender-bridge-ops` 的纪律）；原材质一律 `use_fake_user = True` 保留，别删
4. **执行完另起一次请求独立核验**（全新取引用、重新读 socket 值），不要复用同一脚本的自检
5. **判据取像素级差异**，不要靠肉眼说"看起来一样/不一样"
6. **单次只处理一个矛盾点**，卡住就暂停
7. **部署/复制本材质前先数平面**：目标**不是「三块两两正交且共心的平面」时，必须先停下来提示用户——「要增加/补齐三块平面，做出来才准确」**，确认后再动手；少于三块得不到完整的立体（球形）观感，也别擅自用 1~2 块平面凑合（2026-09-19 实战补充）

## §0 心智模型（三条，先看这个再动节点）

1. **图案 = 只依赖 r 的函数**。`r = |P|`，`P` 是到**共享中心**的坐标。
   于是同一套节点在任意朝向的物体上，切出来都是同心圆 —— 不需要知道物体长什么样。
2. **"发散"= 等值线在空间中的位置**。给函数喂 `r` 再和阈值比较，就得到一圈边界；
   想让它"扩张"就是把阈值随时间推进。**不需要任何方向性逻辑**。
3. **环 = 两个软边相减**。外边界 `R_out`（前缘）和内边界 `R_in`（中心的黑洞）各自独立推进，
   两者之间才是亮的。想要"黑吃掉圆"就是让 `R_in` 追上来超过 `R_out`。

> 反过来说：如果某个"径向"效果只有某个朝向才成立，那它多半不是真的径向场，
> 而是被 UV / 物体朝向绑住了。

## §1 坐标源：一个空物体，而且所有物体必须是**同一个**

这是整套方案的地基，错在这里后面全错。

```python
tc = nt.nodes.new('ShaderNodeTexCoord')
tc.object = ctrl          # ctrl = 一个位于共享中心、单位变换的空物体
r_len = nt.nodes.new('ShaderNodeVectorMath'); r_len.operation = 'LENGTH'
links.new(tc.outputs['Object'], r_len.inputs[0])      # 输出就是 r
```

- `Object` 坐标 = **世界坐标相对该空物体**的坐标 ⇒ 空物体在哪，圆心就在哪
- 空物体必须 **scale=1、无旋转、放在真正的共享中心**。带缩放会把 r 一起缩掉
- 多个共心物体（三块互相垂直的平面等）**全部指向同一个空物体** ⇒ 环天然同心、交线连续
- 同一个空物体**顺便就是控制面**（见 §5），一举两得

**★ 坑：Object 坐标只跟随平移，不跟随旋转。** 转空物体不会让纹理跟着转。
旋转类动画必须在**材质节点内**做偏移（`Math(ADD)`），别指望转空物体。

## §2 节点链模板：径向距离场 → 环形掩码

```
纹理坐标(Object=空物体) ─► 矢量长度 ─► r
                                        │
        ┌───────────────────────────────┤
        │                               │
   Map Range(0..R_out)            Map Range(R_in..R_in+soft)
   To Min/Max = 1..0              To Min/Max = 0..1        ← 注意方向相反
        │                               │
      f_out                           f_in
        └────────────► Math(MULTIPLY) ◄─┘
                          │
                       ring = f_out × f_in
                          │
                    × 强度 ─► Emission Strength
```

**为什么是两个 Map Range 相乘**：`f_out` 在 `r < R_out` 时为 1、之外衰减到 0；
`f_in` 在 `r > R_in` 时为 1、之内衰减到 0。两者相乘 ⇒ **只有 `R_in < r < R_out` 的环带是 1**，
软边落在各自那一侧。这就是"环"的全部。

| 想要的效果 | 怎么给 |
|---|---|
| 光斑（实心圆） | `R_in = 0` 且 `f_in` 剪掉（或 `R_in + soft <= 0`） |
| 环 / 冲击波 | `R_out` 与 `R_in` 一起推进，间距固定 |
| **黑洞吞噬** | `R_in` 从 0 涨到 `> R_out_max + soft` ⇒ `ring ≡ 0` ⇒ 全黑 |
| 辐条 / 射线 | 在 `r` 之外再引入方向 `d = P/|P|` 的周期函数（见 `radial_field.py` 的 `spike`） |
| 循环脉冲 | 见 §4 |

**★ 坑：软边必须落在实体那一侧。** `Map Range` 的 From/To 有两个同名不同类型的插槽
（`VALUE` 与 `VECTOR`），按名字取会取错或报错 —— **按 `(name, type)` 或者索引取**。

## §3 五种模式（都封装在 `scripts/radial_field.py`）

| 模式 | 一句话 | 依赖 |
|---|---|---|
| `spot` | 中心实心圆，边缘软 | `r` |
| `ring` | 圆环（内外两个边界） | `r` |
| `spike` | 从中心射出的辐条 | `r` + 方向 `d` |
| `pulse` | 单次膨胀脉冲（小圆→满圆→黑腔吃光） | `r` + 一条时间链 |
| `cycle` | **四段循环脉冲**（本 skill 的重头，见 §4） | `r` + 循环时间链 |

`cycle` 是独立脚本（`scripts/cycle_pulse.py`），与 `radial_field.py` 的 `pulse` **不共用代码**
（前者多了时间链、空物体属性与驱动器、驱动自检）。**两个脚本各有一处 `split` 的坑，改一处记得看另一处。**

## §4 四段循环脉冲的时间轴（本 skill 最值钱的一节）

需求原型：「开始是纯黑 → 过一段帧数开始扩散 → 填满后停留 → 再被中心漫出来的黑吃成全黑 →
再停留 → 循环」，且**每段时长都要能实时拖**。

### §4.1 循环靠「TVAL ≡ 帧号」的关键帧技巧，不用驱动、不用脚本

```python
# TVAL 是一个 Value 节点，只打两个关键帧：帧 1 -> 1.0、帧 250 -> 250.0
# 全部 LINEAR，再把 F-Curve 的 extrapolation 设成 'LINEAR'
#   => 斜率恒 1、截距恒 0，于是【任意帧上 TVAL 都精确等于帧号】
fc = nt.nodes["TVAL"].outputs[0].driver_add ...   # 不，走关键帧：
nt.nodes["TVAL"].outputs[0].keyframe_insert('default_value', frame=1)
nt.nodes["TVAL"].outputs[0].keyframe_insert('default_value', frame=250)
for c in <该 action 的所有 fcurve>:
    for kp in c.keyframe_points:
        kp.interpolation = 'LINEAR'
    c.extrapolation = 'LINEAR'          # ★ 没有这一条，第 250 帧之后就定格了
```

实测外推到 **1000 帧仍然精确**。比驱动表达式 `frame` 更省心：不依赖
`use_scripts_auto_execute`，也不受"驱动表达式里有东西解析不了"影响。

> 5.x 的 action 是**分层**的，路径是
> `action.layers[i].strips[j].channelbag(...).fcurves`，`action.fcurves` **不存在**。

### §4.2 时间链：周期与相位必须分开

```python
t     = TVAL                                  # ≡ 当前帧
u     = FLOORED_MODULO(t, 周期)                # u ∈ [0, 周期)
v     = u - 变亮前等待                          # 黑场期为负
prog  = clamp(v / 活动, 0, 1)                   # 纯黑期为 0，变黑结束为 1

周期   = 变亮前等待 + 变亮时长 + 全亮维持 + 变黑时长      # 四段之和，自动算
活动   = 变亮时长 + 全亮维持 + 变黑时长
split_out = 变亮时长 / 活动                      # 前缘的归一化位置
split_in  = (变亮时长 + 全亮维持) / 活动          # 后缘（黑洞）的归一化位置
```

然后两条边界各自由 `prog` 推进：

| 段 | `prog` 区间 | `R_out` | `R_in` | 画面 |
|---|---|---|---|---|
| ① 变亮前等待 | `= 0` | `0` | `0` | 纯黑 |
| ② 变亮 | `(0, split_out]` | `0 → 满圆半径` | `0` | 小圆 → 满圆 |
| ③ 全亮维持 | `(split_out, split_in]` | 封顶 | `0` | 满圆保持 |
| ④ 变黑 | `(split_in, 1]` | 封顶 | `0 → 黑洞终半径` | 中心黑腔吃到全黑 |

**★ 两个 `split` 必须不同！** 前缘只由「变亮时长」决定，后缘要等「变亮时长 + 全亮维持」之后才启动。
用一个 ratio 会让"变亮"段被拉长「全亮维持」那么多帧（实测踩过）。

**★★ 时长类参数必须进【相位】，只进【周期】的参数在第一个周期内是空操作。**

这是循环时间轴最容易踩、也最难发现的坑。若某参数**只**出现在 `周期` 里
（不出现在 `u − 参数` / `prog` 里），那么**任何 `f < 周期` 的帧上，两种设置算出的 `u` 完全相同
⇒ 画面逐像素相同** —— 用户拖这个滑块整段没反应，会以为坏了。

实测（改「黑场停留」26 → 120，周期 200 → 294）：

| 帧 | 实测 maxDiff |
|---|---|
| 30 / 150 / 199 | **0.0/255**（逐像素完全相同） |
| 250 / 300 / 350 | 255/255 |

对照：把 10 帧从「等待」挪到「黑场停留」（周期不变）→ **255/255 可见** ⇒ 说明前者真的没进相位。

**正解 = 把黑场放在循环起点**，四段**全部**进相位，四个滑块就都能在首周期内看见。
**排查口诀：参数不变 ≠ 坏，先看它有没有进 `u − 参数`。**

**★ 顺带一个同族现象**：阶段局部参数（如「全亮维持」「变黑时长」「黑洞终半径」）
只在各自阶段可见。停在早期帧拖它们必然无反应 —— 这不是 bug，但**必须写进文档**，
否则用户一定当成故障（实测：用户盯着一个"两边必然相同"的帧，判定"改了没效果"）。

## §5 控制面：空物体自定义属性 + 驱动器（数据驱动，不写面板）

用户的原话需求：「我要**空对象下的数据驱动模式**，不是写一个新的面板」。
所以控制面 = **空物体上的自定义属性**，用**驱动器**打进材质节点插槽。

```python
# 1) 属性：中文键名就是 UI 显示名，顺手带上范围和说明
ctrl["变亮前等待"] = 20.0
ctrl.id_properties_ui("变亮前等待").update(
    min=0.0, max=2000.0, soft_min=0.0, soft_max=600.0,
    description="开始变亮之前的纯黑帧数")

# 2) 驱动器：SINGLE_PROP 变量 → ctrl 的自定义属性
fc = nt.nodes["T_BLACK"].outputs[0].driver_add('default_value')
d = fc.driver
d.type = 'SCRIPTED'
v = d.variables.new(); v.name = 'v'; v.type = 'SINGLE_PROP'
t = v.targets[0]; t.id_type = 'OBJECT'; t.id = ctrl
t.data_path = '["变亮前等待"]'          # 中文键、双引号，一样合法
d.expression = 'v'                      # ★ 变量绑好【再】写表达式
fc.update()                             # 立刻算一次
```

9 个受驱参数：`变亮前等待 / 变亮时长 / 全亮维持 / 变黑时长 / 满圆半径 / 黑洞终半径 /
边缘柔和 / 底色亮度 / 自发光强度`。

**★★ 陷阱一：`driver_add()` 会把表达式自动填成"当时的数值"。**
装完一看 `d.expression == '20.0'` —— 等于装了个**常量驱动**，改属性当然纹丝不动。
**不覆盖 `d.expression` 就是白装**，这一条骗过所有人（本项目被骗了一整轮）。

**★★ 陷阱二：Python 改 IDProperty 不会打更新标记。**
`ctrl["x"] = 33` 走的是 IDProperty 底层接口，**不给物体打 depsgraph 标记**；
而节点驱动是拿**依赖图里的物体副本**去解析属性的，副本没更新就读到旧值。
⇒ **脚本侧必须补 `ctrl.update_tag()`**（再配 `view_layer.update()`）。
探针/脚本里"读回发现没变"十有八九是这个，不是驱动坏了。

> UI 侧（在「物体属性 → 自定义属性」里拖）的行为见 §5.1 —— 两种输入路径**不是一回事**，
> 别用脚本赋值的结果去推断用户在 UI 里拖动会不会生效。

### §5.1 UI 拖动 vs 脚本赋值：两条输入路径

| 输入路径 | 会不会自动打 depsgraph 标记 |
|---|---|
| Python：`ctrl[k] = v` | **不会** ⇒ 脚本侧必须 `ctrl.update_tag()`，否则读回旧值（实测，铁证） |
| UI：在「物体属性 → 自定义属性」里拖数值 | **未隔离实测** —— 仓库从未真测过这条，见下 |

**为什么 UI 那条测不了脚本侧旁证（实测钉死，2026-09-14）：**
① 自定义属性**不出现在 `bl_rna`**（`prop_in_rna=False`，141 个 RNA 属性里没有它）
⇒ `setattr(ctrl, "键", v)` 直接 `AttributeError`，压根走不到 RNA 那条路；
② `bpy.ops.wm.properties_edit` 是 **INVOKE-only** 元数据弹窗（脚本调用报"不支持直接执行"），不是数值框。
⇒ 想判它**只能在 UI 里真拖一次**。

**两段式实测配方**（脚本已随本 skill 带上）：
1. `scripts/probe_ui_tag_arm.py` —— 挂 `depsgraph_update_post` 观察器，把每次更新后的
   「属性值 vs 驱动求值」记进 `scene[KEY]` JSON，取基线。
2. 人在「物体属性 → 自定义属性」里拖一下目标属性（**别换帧、别按播放**，否则污染）。
3. `scripts/probe_ui_tag_read.py` —— **只读回采**：属性值与驱动求值是否同步变了。
   同步变 ⇒ UI 自动 tag（看门狗属冗余保险）；只有属性变 ⇒ UI 不 tag（看门狗必需）。

> 无论结果如何，**看门狗对两种情况都成立**（见母 skill §6 第 3 层），是无脑稳的选择，
> 所以这条空白不影响落地方案，只影响文档敢不敢把"全哑"当结论写。
> 另附 `scripts/probe_tag_path_matrix.py`（单段式）：脚本侧几种写入路径的对照矩阵，
> 把「A 下标赋值 / B setattr / C 操作符 / D 赋值+tag」一次测清，顺带自证了上面①②两条。

**★★ 陷阱三：不要做「假控件」。**
把参数**再镜像一份**到别的 data-block（另一空物体的自定义属性、文本块等），
它会**能拖、有范围、有中文说明，但没有任何连线读它** —— 用户在那边改完全无效。
这是「改了参数没效果」最常见的**误报来源**（本项目实测踩过，排查烧掉好几轮）。
**参数只准有一个入口。**

**★ 自动读数可以做，但不能反向驱动。** 只读的派生值（如「周期帧数 = 四段之和」）
可以给它自己加一条 `IDProperty` 驱动，让它**自动跟随**：

```python
c = ctrl.driver_add('["周期帧数"]')        # IDProperty 也能加驱动
c.driver.expression = 'p0 + p1 + p2 + p3'  # 四个 SINGLE_PROP 变量指向四段时长
```

实测 `全亮维持` 24→174、80→230、40→190，精确跟随。**这比十句解释管用** ——
用户盯着一个不动的死数字，就会判定"逻辑没理顺"（本项目真实案例）。
注意它仍是只读：UI 上能拖，但松手被驱动弹回真实值，description 要写「自动计算（只读）」。
**`ctrl.animation_data_clear()` 必须放在删自定义属性之前**，否则残留驱动指向已删属性。

## §6 验收：把「对称」和「时序」变成数字

**验收一个「循环 + 参数驱动」的成品，最少跑这四件（都有现成手法）：**

| # | 验什么 | 怎么做 |
|---|---|---|
| 1 | 数学层 | 构建脚本自带的 `FAILS=0` + 解析表抽样（覆盖每段边界帧） |
| 2 | 时间层 | **TVAL 外推实测**（抽到 1000 帧仍精确） |
| 3 | 交互层 | **每个参数「改值 vs 默认」的视口抓帧逐像素比对** |
| 4 | 视觉层 | **一个完整周期的视口帧条**（拼接触表，确认分段顺序与接缝） |

- **循环无缝**：跨周期同相位帧逐像素比对，应 **0.0/255**（字节级一致）
- **纯黑干净**：黑场像素实测 **0.000**。Principled 的 `Specular IOR Level` 不清零会有 ~0.025 噪点
- **面板/属性 → 节点联动**：设属性 = 33 → 节点读回 33.00

**★ 判断"用户看不看得见"必须抓视口，不能看 F12。**
视口「材质预览」和 F12 渲染是**两套光照**：前者会用内置 HDRI（`use_scene_world=False`），
后者用场景 world。同一个参数在本项目实测**F12 只变 5/255、视口变 86/255** ——
用 F12 数据下"不可见"的结论是错的。抓法：

```python
bpy.ops.render.opengl(write_still=True, view_context=True)
```
配 `temp_override(window=..., screen=..., area=..., region=...)`。

**★ 判可见性用 maxDiff，不要用"变化像素占比"。**
只有一条边缘在动的参数（如「黑洞终半径」）变化像素可能只占 0.6%，
但 maxDiff 有 223/255 —— 用面积占比会得出"没生效"的错误结论。

## §7 踩坑清单（本路实测）

1. **`Gradient(SPHERICAL)` 的有效半径恒为 1**（源码 `fac = max(0.999999 − |v|, 0)`）⇒ 想做任意半径的径向渐变**别用它**，用 `矢量长度 + Map Range` 自己算。
2. **`MapRange` 有两套同名不同类型的插槽**（`VALUE` / `VECTOR`）⇒ 必须按 `(name, type)` 或索引取。
3. **`Math` 节点的三个入口全叫 `"Value"`** ⇒ 按名字取会**静默失效**，一律用数字索引。
4. **Math 节点的第 3 个输入只有 `MULTIPLY_ADD` 会读** ⇒ 想加三路必须**串两个 ADD**，否则第三路被静默丢弃（实测周期算成 174 而非 200）。
5. **未连接的输入默认是 0.5，不是 0** ⇒ 建节点后要把用不到的口显式清零，否则会混进计算。
6. **材质槽清理"只置 None"会留下空槽** ⇒ 新材质被 append 到**槽 1**，而面的 `material_index` 仍是 0，于是**看起来没换材质**。
7. **5.2 驱动变量类型里没有 `FRAME`**（只有 `SINGLE_PROP` / `TRANSFORMS` / `ROTATION_DIFF` / `LOC_DIFF` / `CONTEXT_PROP`）—— 但**驱动表达式里的内建 `frame` 是可用的**，两者别混为一谈。
8. **`frame * <某个未注册的命名空间函数>()` ⇒ 整条驱动 `is_valid=False`、值恒为 0、画面零变化**。最快的分辨判据是读 **`driver.is_valid`**（变红就是表达式里有东西解析不了），别急着怪 `frame`。
9. **纯 `Emission` 在材质预览里会过曝成白**（强度 ≳3 就把颜色压掉）⇒ 调强度时要同时看视口。
10. **视口是 `SOLID` 模式就永远看不到程序纹理**（只显示 `material.diffuse_color` 单色）⇒ 必须切 `MATERIAL`。
11. **视口「材质预览」与 F12 是两套光照**（见 §6）。
12. **`image.pixels` 的第 0 行是图的【最底部】** ⇒ 拼接触表按行号递增写会**整张上下颠倒**。正确 `dst_row = (ROWS-1-r)*GH + y`。
13. **`image.pixels.foreach_set` 每像素 16 字节**（4 个 float × 4 字节），写成 `4*W*H` 会 `TypeError`。
14. **float32 存 `0.45` 得到 `0.44999998807`** ⇒ 参数回读校验用容差，别做字符串包含判断。
15. **`bpy_prop_collection` 没有 `unlink`** ⇒ 删相机用 `scene.collection.objects.unlink(ob)`。
16. **`ctrl.id_properties_ui(k)` 返回 `IDPropertyUIManager`，不能下标** ⇒ 要 `.as_dict()`。
17. **做像素级坐标换算必须修正半像素**：像素**中心**不在坐标轴上。
18. **「参数无效」要用「渲染 + 逐像素比对」定性**，不要读代码猜；且**探针值必须落在属性的 min/max 内**，否则被静默钳位，看起来像"写入失败"。
19. **动诊断脚本前先 `Read` 一遍被测源码的属性名/节点名。** 一个假阴性（比如把 `T_BLACK` 写成 `T_WAIT`）会把整条排查带偏，浪费好几轮。
20. **EEVEE 只做 per-object 排序**（按物体原点）⇒ 三块共原点的平面互相穿插时排序无意义，**不透明黑区会互相遮挡**，3/4 视角下会叠出六角星般的重叠块。想让画面只看到光不互相挡，掩码应接 `Alpha` 并改用 **`Additive`（加法）混合**（官方明确"加法/乘法混合与顺序无关"，`Alpha Blend` 恰好相反）—— 但那会把"纯黑面板"的语义变成"完全透明"，**这是设计取舍，要先和用户确认**。

## §8 脚本

```
scripts/radial_field.py    # 4 模式构建器（幂等；只清自己，绝不动 src 材质；含回读校验 + 解析表自审）
scripts/cycle_pulse.py     # 四段循环脉冲构建器（TVAL≡帧号 + 四段进相位 + 空物体属性驱动 9 项 + 周期自动读数 + 驱动自检）
scripts/verify_field.py    # T1 径向对称性 / T2 多物体一致性 / T3 时间推进
scripts/shoot_modes.py     # 出参考图；结束自动还原并显式重建成品
scripts/self_test.py       # 隔离试跑：4 模式各建一遍（assign=False），跑完逐项还原场景
scripts/probe_frame_builtin.py     # 定论「驱动表达式里的内建 frame 可用」的五组对照（临时对象，做完删净）
scripts/probe_tag_path_matrix.py   # 脚本侧「写入路径 → 是否自动 tag」对照矩阵（§5.1 ① ② 的数据来源）
scripts/probe_ui_tag_arm.py        # 两段式 UI tag 实测·第 1 步：装观察器 + 记基线
scripts/probe_ui_tag_read.py       # 两段式 UI tag 实测·第 2 步：只读回采 + 判读（§5.1）
```

**跑之前改顶部的模板占位**：`radial_field.py` 与 `cycle_pulse.py` 是**幂等**的，
跑前先看 `CTRL / MAT / SRC / PLANES` 四个名字是不是你工程里的；`self_test.py` / `shoot_modes.py`
顶部的 `FIELD` / `OUT` 是**路径占位**，必须改。桥执行环境里 `__file__` 不可靠，所以都显式定义。
`probe_frame_builtin.py` 用前缀 `__AF` 建临时对象、做完删净，无占位；
`probe_tag_path_matrix.py` / `probe_ui_tag_arm.py` / `probe_ui_tag_read.py` 顶部的
`CTRL / MAT / PROP / NODE / OUT` 五个名字也要改成你工程里的。

`self_test.py` 是**改脚本后必跑**的那一步：它在真实 Blender 里把 4 种模式各建一遍、
校验 `FAILS=0`，然后删临时材质、还原每个 mesh 的材质槽与帧，最后断言场景与基线**逐项一致**。

> 另有一个**面板式**控制方案（addon + `PropertyGroup` + `PointerProperty`，中文滑杆 + 阶段跳帧按钮），
> 本项目已弃用：**和驱动器同时开时两边打架**（面板写插槽 → 驱动器下一次求值又覆盖回去），
> 且用户明确要的是「空物体属性驱动」。要用的话**二选一**。
