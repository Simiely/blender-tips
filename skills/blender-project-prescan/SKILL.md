# 大工程动手前的只读体检（三段扫描）

用途：拿到一个「需要整理」的 .blend，**先出事实与选项，再决定动不动手**。
本 skill 只管「扫描 + 意见清单」；真正执行合并交给 `blender-headless-batch`，清理交给 `blender-scene-cleanup`。

## 铁律

1. **只读扫描先行**，产出报告，绝不直接改工程
2. **先判「磁盘版 vs 运行中实例」**：若 GUI 里开着同一文件且标题栏有 `*`（未保存改动），
   磁盘版就是**滞后的**。报告里必须显式写清以哪个为准
3. 三段扫描**分三次独立进程**跑（各自只读，互不依赖）
4. 报告必须包含**选项对比**（合并成几个、省多少、耗时、代价），不能只给一个数
5. 最后一定给出「需要用户拍板的事」清单

## 通道选择

| 情况 | 通道 |
|---|---|
| 只读扫描、改动 >120s、GUI 打开就卡 | **无头**：`blender.exe --background --factory-startup "<blend>" --python <scan>.py` |
| 要以**运行中的未保存状态**为准 | 9877 桥（`blender-bridge-ops`），需用户点一次 Run Script |
| 工程小 / 只想问一两个数 | 桥 |

无头命令加上 `--factory-startup`（跳过用户插件）与 `--background`（**缺了就变开界面**，大工程是灾难）。

## 三段扫描各回答什么

| 段 | 脚本 | 回答 |
|---|---|---|
| 1 结构 | `scripts/scan_project.py` | 总量与类型分布 / 集合归属 / 材质全清单与引用数 / 目标材质与"单材质目标网格" / 顺带可清项 |
| 2 定向 | `scripts/scan2.py` | 引用源普查 / 目标件明细（父级、世界 bbox、UV、缩放）/ **三种分组口径对比** / 全量合并模拟 / EMPTY 不动点 |
| 3 精查 | `scripts/scan3.py` | **修改器构成** / 三种口径明细 / 多实例对象"共享者是谁" / 相机·输出路径·集合结构 |

配置：三段脚本的 `WORK` **默认取当前工作目录**（报告写 `<WORK>/scan*_report.txt`），
可用环境变量 `BPS_WORK` 覆盖 —— 在哪个目录跑就在哪落报告。
换工程时只需改脚本顶部的**目标材质正则**（`COPPER` / `GOLD` 那些）。

## 动手前必查的四项（缺一就会翻车）

### ① 修改器会不会丢（最容易被忽略）

`bpy.ops.object.join()` **只保留活动对象的修改器**，其余成员的全丢。
Blender 4.1+/5.x 导入的工程常给每个网格挂 **`Smooth by Angle`（按角度平滑，NODES 型）** ——
实测某 SKP 工程 27,352 / 50,622 个对象带它。丢了着色（锐边）就变。

⇒ 扫描必须输出修改器构成；执行时必须**指定一个带该修改器的对象当活动对象**。

```python
mod_name = Counter(m.name for o in objs for m in o.modifiers)   # 实测 {'按角度平滑': 27352}
```

### ② 「多材质就跳过」要看哪种口径

代码里必须**同时报两种**，否则会答错用户：

- 口径 A：`len(me.materials)`（材质槽总数）
- 口径 B：**有面的**槽数（`np.unique(polygons.material_index)`）—— 空槽无几何，Blender 落盘时还会清掉它

实测两者可能相等（无歧义），也可能差一批（有面但槽为空）。**别只报一种就下结论。**

### ③ 分组键 = 材质列表 + UV 层 + 顶点色 + 形态键，**再加"父级"**

前三项是 `blender-headless-batch` 的铁律（UV 不进 key 会被拉平丢失）。
本 skill 补第四项 —— **父级**。因为导入工程的"同类件"往往**按装置分组**：

```
实测：83 个铜件分布在 19 个不同父级下（5 把景观椅各 4 件、2 套地图牌金属字、1 组灯杆锥体…）
      ① 只按材质        → 83 → 7    装置归属彻底消失
      ② 材质 + 父级     → 70 → 11   每组恰好一个装置，还能挂回原父级   ← 通常该推荐这个
      ③ 材质 + 顶层祖先 → 62 → 21
```

**还必须报"单件组"**：只有 1 个对象的组合并收益为 0（1→1），不能算进"省了多少"。

### ④ 多实例红线的"共享者是谁"

`mesh.users > 1` 是合并红线，但要往下再问一句：**共享这份网格的都是谁？**

- 共享者里有**非目标材质**的对象 ⇒ 真红线（会把别人的几何复制 N 份）
- 共享者**全是目标件本身** ⇒ 红线不成立，合并后源网格变孤儿、存盘被丢弃，属正常

## 汇报模板（意见清单必备 9 段）

0. **数据基准警示**（磁盘版 vs 屏幕上的未保存改动）
1. 工程画像（对象/类型/数据块/材质/顶点面/父级比例/**来源与导入器**）
2. 目标材质与目标网格清单（含"被跳过的多材质对象"及其材质组合）
3. ★ **目标件挂在哪**（父级分布 + 顶层祖先分布）—— 决定能不能全局合并
4. 分组口径对比表（①②③ + 单件组说明）
5. **收益的现实评估**（本次能省几个 / 占比，以及"真正的大头是谁"）
6. 风险点（修改器丢失 / 父级摘除 / 多实例定性 / 验证判据与基线数值）
7. 顺带可清项（EMPTY 可删数、空集合、相机、输出路径、孤儿、缺失贴图）
8. 分档建议（低风险档 / 推荐档 / 顺手档）
9. **需要用户拍板的事**（操作通道、目标边界、分组口径、范围）

## 本机踩坑

- **PowerShell 工具不回传 stdout** ⇒ 结果一律 `Set-Content`/`Out-File` 落盘，再用 Read 读
- **`WebFetch` 与 `raw.githubusercontent.com` 均不通**；能用的是 `api.github.com` 与 **`codeload.github.com`**
  （拿整仓最快：`curl -sL -o repo.zip https://codeload.github.com/<o>/<r>/zip/refs/heads/main` 再 `zipfile` 解压）
- **下载走哪条网**（2026-10-02 复测修正）：`api.github.com` **Python 直连即可，不需要代理**；
  反过来，代理没起时无条件走代理会直接 `ConnectionRefusedError [WinError 10061]`。
  ⇒ 稳妥做法是**先探代理端口，通了才用，不通就直连**（`github-api-push` 的 `api_push.py` 已按此改）
- bash 环境不稳（`$(...)` 命令替换、`wc -c < file` 会静默失败）⇒ 关键产物**由被执行的 Python 自己写盘**，
  不要依赖 shell 重定向
- 报告里的中文路径没问题，但**文件名别用 shell 拼**（改用脚本内常量）
- 大工程首次读盘慢、二次读盘走页缓存（实测同一 567 MB 工程：首轮 115s / 次轮 6s）——
  **别用第二轮的时间估第一轮**
