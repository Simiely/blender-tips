# 圆柱「螺旋条纹发光材质」（理发店滚筒）

传输层（9877 桥、`send.py`、120s 上限、Blender 5.x API 坑）见 **`blender-bridge-ops`**。
世界空间**噪波滚动**见 `blender-procedural-emission-material`；**平面**专属坑见 `blender-plane-procedural-material`。
本 skill 专讲**圆柱面**：atan2 角度投影 + 螺旋条纹 + 沿柱上升 + 验收"它真的在上升"。

仓库里的公式出处：`docs/材质与驱动规范.md`（§2 圆柱投影 / §4 驱动 / §5 三大坑）、`docs/技巧速查.md` §17。
那些文档只给公式和参数表，**没有可直接跑的建脚本** —— 本 skill 补上脚本与验收。

## 铁律

1. **先只读侦察**：半径是否恒定（真圆柱）、轴向是哪个轴、世界包围盒与 zmin/zmax、材质槽是否空、UV 层
2. **锚点空物体放"柱底面中心"**，rotation 全 0 / scale 全 1 / 无父级
   ⇒ `Object` 坐标的 z 天然落在 `[0, 柱高]`，v 归一化**少一个减法节点**
   （放几何中心也行，但 v 就要多一次 `−zmin`；放原点则是错的，atan2 极轴会离开柱轴）
3. **改动前放还原点**（复制 .blend，比对字节数）
4. **执行完另起一次请求独立核验**，驱动真值走**求值依赖图**
5. **判据必须能证伪**：上升方向用**垂直互相关**测像素位移，别靠肉眼说"看起来在动"
6. **单次只处理一个矛盾点**，卡住就暂停

## §1 公式与节点链

```
u = (atan2(y, x) + π) / 2π        绕柱角度归一化，0~1（y 是分子、x 是分母）
v = z / 柱高                      高度归一化，0~1（锚点在底面时）
f = u×K + v×N                     K = 环绕圈数，N = 高度条纹数
f = FLOORED_MODULO(f, 1)          ★ 必须 FLOORED
条纹 = ColorRamp(f)  →  ×强度  →  Emission Strength
```

节点链（14 节点 / 15 连线，中文命名便于面板与驱动 data_path 引用）：

```
纹理坐标(Object→锚点) → 分离XYZ
   ├ Y → 柱面_相位角(ARCTAN2)[in0=Y, in1=X] → 柱面_角度偏置(+π) → 柱面_角度U(×1/2π)
   └ Z → 柱面_高度V(×1/柱高) → 上升偏移(+ 驱动) → 高度条纹N(×N)
   柱面_角度U → 环绕圈数K(×K) ─┐
                    高度条纹N ──┴→ 螺旋合成(+) → 螺旋取模(FLOORED_MODULO)
                                                    → 条纹(ColorRamp) → BSDF.Emission Color
                                                       BSDF.Emission Strength（单挂驱动，不连线）
```

- **`Base Color` 设纯黑、`Roughness` 1、`Metallic` 0**：只发光、不反光
- **`Emission Strength` 不连线、直接挂驱动** ⇒ 核验时能读到真值
  （若连线，`default_value` 被忽略，读回 0 是正常的，断言要改成 `is_linked is True`）
- **`ShaderNodeTexCoord.type` 是 `'TEX_COORD'`**，不是 `'TEXCOORD'`；同类：
  `ShaderNodeValToRGB` 的输入 socket 名是 **`Factor`**（不是 `Fac`）
- 原理化 BSDF **别按名字找**（默认名本地化），用 `n.type == 'BSDF_PRINCIPLED'`

### 参数含义与角度速查

| 参数 | 决定 |
|---|---|
| K（环绕圈数） | 柱面上一圈的条纹条数。**必须整数**，否则 u=0/2π 接缝错位 |
| N（高度条纹数） | 高度方向的周期数 |
| K/N 比值 | **螺旋角**（与柱尺寸有关）：`角度 = atan( (K/N) × 柱高 / 周长 )` |

实测样例（半径 3.7789 ⇒ 周长 23.74、高 13.68 ⇒ 系数 0.576）：

| K:N | 角度 | | K:N | 角度 |
|---|---|---|---|---|
| 1:2 | 16° | | 3:2 | **41°** |
| 2:3 | 21° | | 2:1 | 49° |
| 1:1 | 30° | | 3:1 | 60° |

柱面可见斜带数 ≈ K + N。**别照抄文档里的角度表** —— 那张表来自另一个尺寸的柱子。

## §2 ★★ 三个必踩的坑

### 坑 1：ColorRamp 极性 —— 暗底只能靠 `CONSTANT`

**现象**：做出来是「宽白底 + 一条细黑缝」，像把柱子斜着劈开，完全不像灯带。

**根因**：色标 `e0@0(黑) / e1@(1−w)(白) / e2@1(白)`，而插值是 **LINEAR** 时，
`[0, 1−w]` 整段从黑渐变到白 ⇒ 平均亮度极高，只有 f≈0 附近一小条是暗的。

**正解**：`color_ramp.interpolation = 'CONSTANT'` ⇒ `[0, 1−w)` 恒暗、`[1−w, 1]` 恒亮（硬边）。
亮条宽度 = `w` = 亮区占一个周期的比例。

```python
ramp.color_ramp.interpolation = 'CONSTANT'   # ⚠️ 是 ColorRamp 的属性
el = ramp.color_ramp.elements
el[0].position, el[0].color = 0.0, (0,0,0,1)      # 暗底
el[1].position, el[1].color = 0.5, (1,1,1,1)      # 由「条纹宽度」驱动 = 1 − w
el.new(1.0).color = (1,1,1,1)
```

> ⚠️ **`ColorRampElement` 在 Blender 5.2 上【没有】`interpolation` 属性** ——
> 插值方式是整个 ColorRamp 的 `interpolation`。写 `el[i].interpolation` 会 AttributeError。
>
> **暗部必须是纯黑**：暗部非黑 ⇒ 暗区也会微微发亮，"灯带"感全失。

### ★★ 要「能调的渐变」⇒ 波形放 Math 域，不要让 ColorRamp 兼职

**v1 的错误做法**（记录在此以免重犯）：把波形编码进 ColorRamp 的 6 个**色标位置**，
4 个位置挂驱动。结果三个死结：

| 症状 | 根因 |
|---|---|
| 用户抱怨"色标拖不动" | 中间 4 个色标被驱动锁死 |
| 改一个滑块会同时改亮峰位置/前缘/后缘 | 三个参数挤进一个耦合公式 |
| 拖尾长度上不去（w=0.4 时最多 58%） | 拖尾空间 = `1 −(亮峰+半宽)`，结构性受限 |

**根因一句话：用「颜色节点的色标位置」去编码一条数学曲线，是把几何信息塞进了颜色容器。**

**v2 正解 —— 波形在 Math 域显式构造**（依据 Blender 手册：`Map Range` 有 Smooth Step
插值；`Math → Wrap` 用于"repeat automatically as the input increases"）：

```
p     = FLOORED_MODULO((u + spin) × K, 1)
前缘  = MapRange(SMOOTHSTEP,  0 .. A  →  0 .. 1)      # A = 前缘宽度
拖尾  = MapRange(SMOOTHSTEP,  B .. 1  →  1 .. 0)      # B = 拖尾起点
mask  = MINIMUM(前缘, 拖尾)                             # 取包络 ⇒ 快升/平台/慢降
```

- `A`、`B` **正交、语义单一**，而且都挂在 **socket** 上 ⇒ 驱动路径就是 `inputs[N]`，
  比 `'...color_ramp.elements[i].position'` 稳得多
- **拖尾长度 = 1 − B**，能开到 99%（v1 上限 58%）
- `p=0` 与 `p=1` 处 mask 都是 0 ⇒ **首尾同值，绕一圈无缝**
- `A = 1−B` 时退化成对称条纹（所以"对称"是特例，不是另一套代码）

**ColorRamp 从此只管颜色，一个驱动都不挂** ⇒ 用户双击进去随便加色标。
左端 = 不发光色、右端 = 发光色，中间可加色标做多段渐变。

`MapRange` 实测签名（Blender 5.2）：
`inputs = [0]Value [1]From Min [2]From Max [3]To Min [4]To Max [5]Steps`；
`interpolation_type ∈ {LINEAR, STEPPED, SMOOTHSTEP, SMOOTHERSTEP}`；`clamp` 是 BOOLEAN。

**验收要点**：这种"参数挂在 socket 上"的设计，可以让核验脚本直接读 `inputs[N]` 的
**求值真值**来断言，不需要读 ColorRamp 色标，断言更稳。

## §3 上升 / 旋转的方向

条纹是斜的 ⇒ **对螺旋条纹，"竖直平移"与"水平平移"都只是改变截距**（沿条纹自身方向平移图案不变）。
所以"螺旋上升"用**竖直平移**即可：在 v 上加偏移。

```python
# 上升偏移 = −frame × 上升速度      ⇒ 正速度 = 条纹【向上】流动
bind_drive(nt.driver_add('nodes["上升偏移"].inputs[1].default_value', -1),
           '-fr * us', {'fr': ('SCENE', scene, 'frame_current'),
                        'us': ('OBJECT', ctrl, '["上升速度"]')})
```

推导：`f = uK + (v+Δ)N`，等值线 `v = (c−uK)/N − Δ` ⇒ Δ 减小 ⇒ v 增大 ⇒ 上移。
Δ = −frame×速度 ⇒ 正速度让 Δ 递减 ⇒ **向上**。

**速度换算**：速度 = 0.02 ⇒ 走完整根柱高需 `1/0.02 = 50` 帧。
反向填空值即可。

### 坑 7：★★ 隔离临时场景渲染时，节点树驱动不会被求值

**现象**：`evaluated_get(dg).node_tree` 读到的驱动值**全对**（K=4 / spin=-3.65 / 强度=0.6），
但渲染出来是**建材质时的旧 default**（K=1 / spin=0 / 强度=1.0）。
改 `default_value`、link 控制空物体进临时场景、切活动场景、`depsgraph.update()` —— **全都没用**。

**症状的迷惑性**：数值验证（核验脚本）全绿，只有渲染不对，极易误判成"材质坏了"。

**处置**（按可靠性排序）：
1. **改 ctrl 的值**（让值真的变化）+ `touch()` ⇒ 生效。诊断脚本 s64 就是靠这个让 K 扫描出效果
2. 要渲染**固定**参数时：**把驱动整个移除**（`node_tree.animation_data_clear()`），
   手动把值烘进 `default_value`，渲染完再 `exec` 建脚本恢复驱动
3. 别指望 `update_tag()` / `view_layer.update()` / `depsgraph.update()` 能解决

### 坑 8：`bpy.data.images` 按【文件路径】缓存

渲染覆盖同名 PNG 后再 `load()`，拿回的是**第一次的旧像素**。
症状：连续多次运行"结果完全相同"，**连文件字节数都一样**，于是白排查很久。

**处置**：每次渲染用**唯一文件名**（时间戳后缀），或 load 前先
`for im in list(bpy.data.images): if 同路径: remove(im)`，并 `im.reload()`。

### 坑 9：`Image.pixels` 对 PNG 返回的是 **sRGB 编码值**

不是线性值。证据：发光强度设 0.6 时读数上限 = **0.7974 = sRGB(0.6)**。

**处置**：要拿线性亮度必须自己反解
`s = np.where(v<=0.04045, v/12.92, ((v+0.055)/1.055)**2.4)`。
（对比"形状"时用相关系数可绕过，但要比绝对值就必须反解。）

### 坑 10：`ortho_scale` 对应的是【较长边】，不是水平边

本机实测：分辨率 420×900、`ortho_scale = 15.5` ⇒ 水平比例是 `900/15.5 = 58.06 px/单位`，
**不是** `420/15.5 = 27.10`。用错会让你只采到柱面中间一小段，
把 K=4 的 1.59 个周期**误判成"只有 1 个周期"**（我这个坑害了自己很久）。

**自检方法**：量柱子在画面里占多少像素。半径 3.7789 柱子在 420px 宽里占满整幅
⇒ px/单位 ≈ 55.6，与 58.06 吻合、与 27.10 差一倍。

### 坑 11：断言"渲染像素 vs 理论曲线"时，φ 空间映射务必先自证

端到端验证（本 skill §4）最容易错的就是屏幕坐标 ↔ 柱面角度 φ 的映射。
**先做三件事再比数值**：
1. 量柱子在画面里的像素跨度，反推 `px/单位`
2. 检查垂直方向亮度起伏（竖条纹必须 ≈ 0，实测 0.0001）
3. 数一遍渲染出的亮带条数是否等于 `Δu × K`（可见弧 Δu ≈ 0.5）

对齐之后相关系数会从 0.07 直接跳到 **0.9989** —— 差别全在映射，不在材质。

## §3b 同源变体：竖条旋转（条纹绕 Z 轴转）

同一套柱面坐标，**去掉高度项 v**、把相位换成"绕轴转动"：

```
f = (u + spin) × K     spin = −frame × 旋转速度
```

- **无 `v` 项 ⇒ 条纹是竖直母线，不倾斜** —— 节点链里 `分离XYZ.Z` 完全不接任何东西
  （可以拿这条做断言：「无任何连线从 Z 出发」= 确实与高度无关）
- **`spin` 必须加在【乘 K 之前】** ⇒ 转速与条纹条数解耦
  （加在之后：改 K 会连带改转速；而且 `f = u×K + spin` 的 `spin` 语义变成"平移 K 个单位"）
- 取模同样必须 `FLOORED_MODULO`（负速度时 `f` 取负）
- 锚点仍然是「柱底面中心」（本路不用 v，但 `atan2` 的极轴必须在柱轴心）
- **两个变体各占一个材质槽，可并存**：侧面挂条纹那份，端盖挂纯黑（见坑 5）

**方向约定**：`spin = −frame × 速度`，正速度 ⇒ `spin` 递减 ⇒ `u + spin` 递减。
`u` 增大 = 俯视逆时针 ⇒ 正速度 = **俯视逆时针**（正视图上条纹向右移）。

**★ 观感陷阱：K 重旋转对称**。K 是整数 ⇒ 绕轴转 `360/K` 度图案完全重合。
实测渲染 0/90/180/270 四个侧面角度，K=4 时**四张图几乎一模一样** ——
用户会因此说"这不像是绕轴转的，像某种对称"。

**K 小还会被柱面投影放大成"色块感"**：屏幕 `x = R·sin φ` 非线性 ⇒
中央拉伸、边缘压缩，正面永远是"中间宽两边窄"。实测（同帧同参数）：

| K | 正面观感 |
|---|---|
| 4 | 一条宽白带，像被切成两半 |
| 6 | 三道光带，明显是"绕柱的竖条纹" |
| 8 | 更密，灯管感更强 |

⇒ **用户说"不像绕柱条纹"时，先看 K**，建议 6~8。

### §3c ★★ 滚筒斜纹：加高度项，且【方向必须实测标定】

`f = u×K − v'×N`（`SUBTRACT`）⇒ 条纹是 `/` 形（左下→右上）。
节点：`Z → ×(1/柱高) → 高度V → +上升偏移(驱动) → ×N(驱动) → 螺旋合成(SUBTRACT) → 取模`。

**★ 方向由实测决定，纸面推导会推反：**

| 驱动表达式 | 两帧间暗带位移 | 结论 |
|---|---|---|
| `−fr * us` | `+0.29 / +0.32`（右移） | ✗ 不是要的方向 |
| **`+fr * us`** | **`−0.32 / −0.29 / −0.28 / −0.19 / −0.21 / −0.31`（左移）** | ✔ 右下→左上 |

我在纸面上推过一遍，推出"负号才对"，**实测是反的** —— 白写了一遍代码。
教训：**这类符号问题不要推理，要测量。**

**怎么测**（`scripts/shift_check.py`）：在渲染图上取**固定高度的一行**，
找暗带（低于阈值）的连续段中心 x，比较两帧的归一化 x ⇒ 位移符号即运动方向。
（斜条纹沿自身方向平移看不出位移，所以必须"横切一刀"看剖面移动。）

**斜角**：`atan((K/N) × 柱高 / 周长)`。K:N = 3:2 ⇒ 41°（本柱周长 23.74 / 高 13.68）。
可见斜带数 ≈ K + N。

### §3d ★ 让「斜角」直接可控（别让用户去凑 K:N 比值）

把高度周期数 `N` 做成**派生量**，由斜角经节点链实时反算：

```
斜角(度) ─RADIANS→ 弧度 ─TANGENT→ tanθ ─┐
条纹数量K ─× (柱高/周长) ───────────────÷──→ N ─→ 高度条纹N
```

- 常数 `柱高/周长` 直接写进节点（本柱 0.5761，换工程要重算）
- **`K` 保留为控件、`N` 变成显示量** —— 用户要的"条纹数和角度都要"就这样同时满足
- 面板底部实时显示反算出的 `N`，**改 K 时斜角自动保持**
- `N` **不必整数**（柱高方向不闭合、端盖又是黑的）；`K` **必须整数**（绕柱方向闭环）
- 实测（K=3 固定）：20°⇒N4.75 · **41°⇒N1.99** · 65°⇒N0.81

⚠️ 核验时注意：`RADIANS` 节点的**输入是度数**，换算在节点内部完成；
   输出端被连线占用、`default_value` 不参与求值 —— 断言要读**输入**，别读输出。

## §4 ★★ 验收：证明它"真的在上升"

肉眼看三帧"好像往上走了"不算证据。用**隔离临时场景 + 垂直互相关**给数字：

1. 新建临时场景，**额外 link** 目标对象（❌ 不要 unlink 主场景；❌ 不要新建只属于临时场景的物体
   —— 那样材质不在被求值的依赖图里，驱动全程不生效，整轮数据作废）
2. 世界背景设纯黑；正交相机沿柱**法线**摆（`center + dir×60`），`ortho_scale = 柱高 × 1.1`
   - `ortho_scale` 对应**较长边**：竖构图时它管高度，宽度 = `ortho_scale × 宽/高`，
     必须 `> 柱直径`，否则柱子被左右裁掉
   - 相机 `local +Y` 经 `to_track_quat('-Z','Y')` 对齐世界 +Z ⇒ 图像竖直方向 = 世界 Z
3. **`sc.render.dither_intensity = 0.0`** —— 默认 1.0 会给像素加 ±1/255 抖动，
   相关峰值会崩（实测 1.0 → 0.376），位移估计直接失效
4. `sc.render.filepath = <绝对路径>` **必须先设**，否则 `write_still=True` 静默不写盘，
   而 `os.path.exists` 还会被旧文件骗过
5. 换帧要调**主场景**（帧驱动指向主场景），再 `view_layer.update()`
6. 逐帧读像素做垂直剖面（沿行方向平均），扫描位移找最大相关

**判据定义**（容易搞反，写清楚）：
`np.roll(b, d) ≈ a` 表示 b 的内容出现在**更大的行号**处；Blender 图像**行 0 = 最底行**
⇒ 行号大 = 位置高 ⇒ **d < 0 意味着 b（后帧）内容更高 = 上升**。

实测（柱高在图上 934 px，速度 0.02，帧间隔 10）：

| 帧差 | 实测 | 几何预期 `0.02×10×934` | 相关 |
|---|---|---|---|
| f365→f375 | **−187 px** | −187 px | 0.979 |
| f375→f385 | **−186 px** | −187 px | 0.977 |

> ⚠️ **搜索范围要够大**：`±120` 会撞边界给出假的 −120，必须 ≥ `速度×最大帧差×柱高像素 × 2`。

**用完清理**并自证：`leftover_objects/scenes/worlds` 全空 + 对象/场景/世界/材质计数回到基线。
（临时场景想删掉，得先把 `bpy.context.window.scene` 指回主场景。）

### 旋转（竖条路）怎么测 —— 别照搬垂直剖面

旋转产生的是**水平**位移，判据要换：

1. 用**列剖面**（对行求平均），不是行剖面
2. ⚠️ **不能直接在屏幕空间互相关** —— 柱面投影 `x = R·sin φ` 是非线性的，
   位移会被 `cos φ` 压缩；再用窄带更糟：K=4 时一个条纹周期在中央占 253 px，
   ±60 px 的带可能整段同色 ⇒ 剖面是常量、相关度 NaN
3. **正解：把屏幕像素重采样到柱面角度 φ 空间**（取样列 `x = R·sin φ`），
   在 φ 空间里"旋转"就是**纯平移**，曲率偏差归零：

```python
PHI = np.linspace(-1.25, 1.25, 501)              # ±71.6°，避开 |φ|→90° 采样退化
X_PIX = R_CYL * np.sin(PHI) * px_per_unit_x + RES_X / 2
prof = lambda row: np.interp(X_PIX, np.arange(wpx), row)
```

4. 相位真值从驱动读：`Δφ_预期 = 2π × Δframe × 旋转速度`

**顺带**：跑这种"改控件→渲染→再还原"的扫描脚本时，还原后要断言
（见坑 6 —— 我就是在演示脚本里把用户的色标改坏过一次）。

## §6 核验清单（另起一次请求）

**结构**：锚点位置/rotation/scale/无父级 · `tex.object is ctrl` · 节点齐全 · **连线逐条断言**
（别只数总数）· 无 MapRange/图像节点残留 · `FLOORED_MODULO` · `ColorRamp.interpolation == 'CONSTANT'` ·
色标 0 暗 / 1 亮 · Emission Strength 未连线 · 驱动 5 条齐全且 `is_valid` · 变量全是 `SINGLE_PROP` ·
文本块存在且 `use_module` · 看门狗在线 · 面板类已注册 · 对象面数不变
**行为**：逐个改控件 → **主动 tag → 从求值依赖图读回**（`mat.evaluated_get(dg).node_tree`）→
逐项对期望 → 最后还原默认值并断言还原成功

⚠️ 四条写断言时的坑：
1. **节点不是 ID 数据**，bpy 每次访问返回新 wrapper ⇒ `l.to_node is node` **恒为 False**，
   断言会静默空跑。必须比 `.name`。
2. 看门狗不能拿 `as_module()._watch` 去问 —— `as_module()` 可能重载模块产生新对象。
   要读 `register()` 存进 `driver_namespace` 的那个引用。
3. 期望值写成引用默认值表（`DEF['环绕圈数']`），别硬编码 —— 否则调默认值时断言全废。
   **但公式本身要在核验脚本里【独立重算一遍】**（用与驱动表达式不同的写法，如 Python 浮点中间量），
   否则"同源复算"会把公式错误一起掩盖过去。
4. **阈值型断言必须从几何/物理上限推导，不能拍脑袋。** 实测踩过：写"拖尾 > 亮带 × 1.5"，
   而拖尾的物理上限是 `1 − (c + w/2)`，`w = 0.4` 时倍率最多 1.45 ⇒ 这条断言**恒假、永远红**，
   而功能其实是对的。改成断言"拖尾铺满剩余空间（色标4 = 1.0）"这种**有明确上限的等值**才不会误报。
