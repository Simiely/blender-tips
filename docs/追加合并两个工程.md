# 追加合并两个 `.blend` 工程

> 来源: `261001x02x环境_优化版.blend`（A，环境） + `261002x03_优化.blend`（B，主形象） 实战
> (A: 164 对象 / 10,197,620 顶点 / 64 材质 / 42 图像 / 257.9 MiB)
> (B: 29,914 对象 / 18,734,068 顶点 / 277 材质 / 140 图像 / 363.5 MiB)
> 适用: Blender 5.2.2 LTS
> 脚本包: 随 skill 自带 [`skills/blender-blend-append-merge/scripts/`](../skills/blender-blend-append-merge/scripts/)
> Skill: [`skills/blender-blend-append-merge/`](../skills/blender-blend-append-merge/)
> 动手前的只读体检: [`skills/blender-project-prescan/`](../skills/blender-project-prescan/)

## 场景

两个工程本来各干各的：一个搭好了**环境和渲染设置**（相机、帧范围、输出路径、世界），
另一个装着**主形象**。要合成一个工程出片，或者要把两份模型放进同一个场景里对齐。

这和 [按材质合并为单个网格体](按材质合并为单个网格体.md) 完全是两件事：

| | 按材质合并 | 追加合并两个工程 |
|---|---|---|
| 目的 | 减少**对象数**，治 GUI 卡顿 | 把两份**内容**并进一个文件 |
| 手段 | `bpy.ops.object.join()` | `bpy.ops.wm.append()` |
| 主要风险 | 几何被**重复计入**、模型散架 | **丢件**（游离对象）、**名字错位** |
| 可逆性 | 不可逆（单体选择能力消失） | 可逆（两条并行子树随时能分开） |

> ⚠️ **别把两者混着做**。为了「让 append 快一点」而先对来源侧做按材质合并是**负收益**：
> 导入工程里大量对象共享同一 mesh 数据块，合并必须**独立化**实例 ⇒ 几何被展开 ⇒ 文件暴涨。
> 实测同一个来源工程：按材质合并产物 **654.7 MiB > 源 540.8 MiB**。

## 权威依据(先查再做)

### 1. 官方手册

`files/import_export/append_append.html`：

> *"Append … creates a copy of the data-blocks from the source file in the current blend-file.
> … Append can be used to … add objects, collections, materials, etc."*

要点：**append 是「复制数据块进来」，不是「合并场景」**。这就直接推出两个推论：

* **场景级设置不会跟过来**（见「机制细节」）—— 底文件是谁的，产物就是谁的设置；
* **重名的数据块会被改名**，而不是被合并（见坑 1）。

### 2. 运行时 API 自省

```python
import bpy
print([p.identifier for p in bpy.ops.wm.append.get_rna_type().properties])
```

实测 Blender 5.2.2 的可用参数：

```
filepath, directory, filename, files, check_existing, link,
do_reuse_local_id, clear_asset_data, autoselect, active_collection,
instance_collections, instance_object_data, set_fake, use_recursive
```

> ⚠️ `do_reuse_local_id=True`（"尽量复用已有的本地数据块"）**实测无效**：
> 同名且**节点树指纹完全相同**的材质依然被复制成 `X.001`。别指望它去重。

## 机制细节

### 为什么「以谁为底」差 80 倍

append 的成本几乎全在**为每个对象建本地副本、逐个做全局唯一名校验、逐个挂依赖**上，
这是一条**硬性单线程**的 C 路径。顶点数据是按数据块走 memcpy / 反序列化，
占比小得多；贴图同理。

实测同一对工程：

| 方向 | 被追加进来的对象数 | 被追加的几何 | append 本体耗时 |
|---|---|---|---|
| **A 为底** → 追加 B 的 `SKP Imported Data` | 29,914 | 18.73 M 顶点 | **457.9 s** |
| **B 为底** → 追加 A 的 `SKP Imported Data` + `相机` | 154 | 10.20 M 顶点 | **7.0 s** |
| A 为底 → 只追加 1 台相机 | 1 | 0 | 约 1.4 s（纯库打开开销） |

★ **几何量差 1.8 倍，耗时差 80 倍**。约合 **15 ms / 对象**。

⇒ **估时看「被追加侧有多少个对象」，不要看文件体积或顶点数。**
本仓库早先记的「能省一半时间」是两个数量级的低估。

### 为什么不能靠对象名对账

Blender 的唯一名算法在最后一个 `.NNN`（**纯数字**）处切分基名：

```
G-物体.010   →   基名 = "G-物体" , 序号 = 10
```

所以当底文件里已经有大量 `G-物体.NNNNN` 时，追加进来的 `G-物体` 会被分配到
**该组里第一个空闲号**（实测 → `G-物体.47361`），被顶掉的位置再往后挤，形成**链式挪号**。

**关键**：这是**置换**，不是丢失 —— `G-物体.011` 这个名字在产物里和来源侧都存在，
只是**换了主人**。所以：

* 名字集合的差集**几乎为空**（实测只差 3 个新最大值），
  拿它去量「改了多少名字」会**全部漏报**；
* 用脆弱的名字映射校验父级名会得到一个**没有意义**的数字（实测 2,894）。

**正确的量化口径** —— 用「除名字外全属性结构键」配对：

```python
# 键 = (类型, 顶点数, 面数, 材质槽数, 修改器数, 位级世界矩阵)
keyB = collections.defaultdict(list)
for nm, v in BASE.items():
    keyB[(v["t"], v["nv"], v["np"], len(v["m"]), len(v["mo"]), tuple(v["mw"]))].append(nm)
keyA = collections.defaultdict(list)
for n in new:
    r = PROD[n]
    keyA[(r["t"], r["v"], r["f"], len(r["m"]), len(r["mo"]), r["mw"])].append(n)

shifted = 0
for k, namesB in keyB.items():                 # 键组内：除名字外完全一样
    namesA = keyA.get(k) or []
    shifted += len(namesB) - len(set(namesB) & set(namesA))
```

实测：**结构键 100% 可配对**（0 个键组找不到对应），其中 **1,026 / 29,914（3.4%）** 名字被改。

### 为什么世界矩阵多重集是「层级 + 变换」的总账

`matrix_world` 已经是**绝对世界坐标**，父级链只要有一环错、或者某个变换丢了，
世界坐标立刻错，多重集马上不等 —— 一条判据同时覆盖两件事，而且**完全不依赖名字**。

```python
# ① 位级：raw 16-float 元组的多重集逐一相等（最强判据）
exact = Counter(tuple(v) for v in mw_B) == Counter(tuple(v) for v in mw_new)

# ② 容差：逐列排序后逐点比 —— 免疫 float32 末位抖动（|v|≈5000 时 ULP≈6e-4）
for j in range(16):
    for x, y in zip(sorted(v[j] for v in mw_B), sorted(v[j] for v in mw_new)):
        assert abs(x - y) <= 2e-3 + 1e-6 * abs(x)
```

**为什么「逐列排序」而不是靠名字配对**：同一列上若有两个对象值相同，谁配谁都不影响
排序后的标量序列 —— 这既是多重集语义，又天然容忍 ULP 抖动。真有一个对象变换错了，
排序序列会出现 O(1) 的错位，立刻被抓到。

## 坑(逐条实测)

### 1. 游离对象会被整批漏掉 ★最容易被忽略

append 一个集合，只会带**该集合树里**的对象。但导入工程常有几个对象
**直接挂在 Scene Collection 根下**，不属于任何 `bpy.data.collections`：

```python
covered = {o.name for c in bpy.data.collections for o in c.objects}
miss = sorted({o.name for o in bpy.data.objects} - covered)
```

实测来源侧有 3 个：`G-3d66-Edi961475.001` / `Mesh1` / `Mesh2`。
**它们不是垃圾** —— 都在主体位置、`visible=True`、`hide_render=False`，
各带 8,184 / 10,526 / 21,092 顶点和正常材质。漏掉就是**模型缺件**。

⇒ 对漏掉的对象逐个单独 append（每个都重开一次库，固定开销约 1.4~1.8 s）：

```python
bpy.ops.wm.append(filepath=os.path.join(SRC, "Object", name),
                  directory=SRC + os.sep + "Object" + os.sep, filename=name,
                  instance_collections=False, set_fake=False, use_recursive=False)
```

### 2. 重名去重会「按数字后缀续号」

见「机制细节」。**链接、变换、几何全都对（实测位级一致），但名字不可靠。**
任何「按对象名找回来源侧对象」的脚本都会失败。

要保名就在 append **之前**给来源侧副本统一加前缀，**不要**事后改。

### 3. 场景设置与「同名 World」的真相

实测：底文件 `scene.world` 引用**从不变**，来源侧的 `World` 根本不会被带进来 ——
所以「两个工程都有名叫 `World` 的世界、但节点树不同（A 3 节点 / B 2 节点）」
这个看起来吓人的隐患**其实不会发生**。

fps / 帧范围 / 输出路径 / 场景相机 / 引擎 / 分辨率 **14 项逐项验过，全部保持底文件的**。

反过来说：**以 B 为底就会丢掉 A 的这些设置**，而场景级设置的归位没有可枚举的边界
（`scene` + `render` + `cycles` + `color_management` + view layers + 合成树…）——
这就是「不要为了省 7 分钟去选对象多的一边当底」的理由。

### 4. excluded 集合的 exclude 状态会丢

底文件里被 exclude 的集合（如 `Export`，里面 5 个对象不在视图层）**本身不动**；
但如果你是**以来源侧为底**，被追加进来的一侧其 exclude 状态会丢失 ⇒ 那些对象会冒出来参与渲染。

### 5. 同名材质内容完全相同也会复制成 `.001`

5 个同名材质（`Brain1` / `Concrete 04 [imported]` / `DefaultMaterial` / `Glass` / `石膏 (1)`）
经节点树指纹判定**内容完全一致**，append 后仍生成 `X.001`；`do_reuse_local_id=True` 实测无效。

代价可忽略（341 个材质里多 5 个，外观一致）。要收干净就按指纹把 `X.001` 的材质槽
重映射到 `X` 再删。

### 6. `Render Result` / `Viewer Node` 不会跟过来

它们是 `source = "VIEWER"` 的生成型图像，没有对象引用它们 ⇒ 不参与依赖闭包。
实测新增图像数 = 来源侧图像数 **− 2**。这正是它该有的行为，别当成丢件。

### 7. 存盘必须排在对账【之前】

实测踩过：对账里一个 `%` 格式化 bug（单个 `%s` 的右操作数是三元组时，Python 把元组
当作多参数解包）让脚本**在存盘前崩溃**，8 分钟 append 全部白跑。

⇒ 流程写成 **append → 快照 → 存盘 → 对账 → 写报告**。报告出问题也不丢产物。

### 8. 取整位数不一致会全域假报

基线用 `round(v, 6)` 存、产物用 `round(v, 5)` 比 ⇒ 双重取整，29,914 个对象**全部**报不匹配。
两侧取整位数必须一致，或者干脆都走容差口径。

### 9. 「A 侧不变性」的判据别写成总数相等

追加必然让材质 / 图像 / 集合等**总数变大**，写成 `before == after` 会全红。
正确判据是「A 原有的**每个条目仍在且值不变**」。

## 验证

### 两层，缺一不可

**① 进程内对账**（脚本自己算）：A 侧逐对象不变 + B 侧多重集守恒 + 总量 = A + B。

**② 独立复核**（**必须另开一次 Blender**）——「①」只证明内存里的数据对得上，
**不证明存出去的文件还能打开**：

```bash
blender.exe --background --factory-startup "<产物.blend>" --python verify_append.py
```

判据：

```
A 原对象一个不少 / 逐对象未变            OK
A 原有 6 类数据块条目仍在且值不变        OK
★世界矩阵多重集 == B（位级完全一致）      OK
逐对象签名 / 顶点 / 面 / 数据块 / 资源     OK
B 的 3 个游离对象已并入                  OK
场景相机 / fps / 帧范围 / 输出路径 == A  OK
VERIFY_RESULT: PASS      REOPEN_OK
```

### 实测结果

| | 结果 |
|---|---|
| 进程内对账 | **PASS 33 / FAIL 0** |
| 独立复核（另开 Blender） | **PASS 28 / FAIL 0** + `REOPEN_OK` |
| 世界矩阵最大元素偏差 | **0.000e+00**（位级完全一致） |
| 顶点 / 面 | 28,931,688 / 28,094,181 = A + B（逐位相等） |
| 多实例 | 25,091 保持共享，**未展开成实体**（文件不因实例膨胀） |

## 性能：耗时到底花在哪

```
载入底文件                  1.5 s
append 集合               457.9 s     ← 98.8%，全在 29,914 个对象上
append 3 个游离对象          5.4 s
快照 30,078 个对象           33 s
存盘 620 MB                  0.9 s     ← zstd 压缩，出乎意料地快
对账                         0.3 s
```

反直觉的两点：

* **几何量和耗时几乎无关**：A 侧 10.2 M 顶点只花 5.6 s；B 侧 18.7 M 顶点花 458 s。
  差的是**对象数**（137 vs 29,914），不是数据量。
* **存盘 620 MB 只要 0.9 s**：文件体积不是时间大头，不必为「先瘦身再存盘」费心。

### 多线程为什么不行

`bpy.data` 不是线程安全的，`append` / `join` 都是**硬性单线程**。
实测 32 线程下 3 秒 CPU 增量只有 2.95 s —— 只有一个核在转。
`--threads` 只管渲染和物理模拟，**对数据块操作无效**。

## 实测产物形态

```
对象 164 -> 30,078 （MESH 27,472 / EMPTY 2,584 / CAMERA 22）
顶点 10,197,620 -> 28,931,688 = A + B（逐位相等）
面    7,957,765 -> 28,094,181 = A + B（逐位相等）
材质 64 -> 341   图像 42 -> 180   网格块 80 -> 2,860
节点组 0 -> 1    相机 21 -> 22    集合 5 -> 8
体积 257.9 MiB + 363.5 MiB -> 620.8 MiB
```

集合结构保持「**两个并行子树**」：

```
Scene Collection
├── SKP Imported Data              ← A（环境），原树分毫未动
│   ├── SKP Mesh Objects            137 对象
│   └── SKP Scenes (as Cameras)     5 相机
├── SKP Imported Data.001          ← B（主形象），整树带 .001 后缀
│   ├── SKP Mesh Objects.001        29,910 对象
│   └── SKP Scenes (as Cameras).001 1 相机
├── 相机                            17 相机（A）
├── Export                          5 对象，exclude=True（A）
└── (3 个游离对象)                  G-3d66-Edi961475.001 / Mesh1 / Mesh2
```

这是最安全、可区分来源、可回退的形态。若要求结构统一，事后改名 / 挪集合即可 ——
但**不要**把来源侧的名字改回原名，会再次触发坑 2 的挪号。

## 自测台(可复现)

`scripts/smoke/` 是一对合成场景生成 + 语义测试，**8 个对象、0.007 s** 就能覆盖 append 的全部语义：

```bash
SMK_TAG=A blender.exe --background --factory-startup --python build_smoke_ab.py
SMK_TAG=B blender.exe --background --factory-startup --python build_smoke_ab.py
SMK_ROUTE=op blender.exe --background --factory-startup smoke_A.blend --python append_test.py
```

场景逐条覆盖：集合同名 / 对象同名 / 材质同名（内容一致）/ NODES 修改器引用 NodeGroup /
多实例 mesh / 父级链 + EMPTY / 打包贴图 / 世界同名（内容不同）/ 相机同名。

实测输出（可直接当「append 到底做了什么」的参考基准）：

```
集合    SKP Imported Data -> SKP Imported Data.001（并行子树，原树分毫不动）
对象    G-物体 -> G-物体.001（原对象不动）
材质    M_shared -> M_shared.001（内容相同也复制，do_reuse_local_id 无效）
网格    3 个对象共用一份 mesh -> 仍共用，users 仍为 3（★文件不会因实例展开而膨胀）
修改器  NODES 修改器引用的 NodeGroup 自动跟随带入
贴图    打包图像自动跟随带入
世界    底文件 scene.world 不变，来源文件的 World 不进来
```

拿 364 MB 工程去试错代价太高，改脚本逻辑时先跑这个。
