# 按材质合并为单个网格体

> 来源: `S:\download\261001\261001x02\261001x02x环境.blend` 实战
> (SketchUp 导入工程:510 MB / 24,481 个网格对象 / 10,197,620 顶点 / 7,957,765 面 / 64 材质)
> 适用: Blender 5.2 LTS
> 脚本包: [`scripts/merge-by-material/`](../scripts/merge-by-material/)
> Skill: [`skills/blender-headless-batch/`](../skills/blender-headless-batch/)
> 动手前的只读体检: [`skills/blender-project-prescan/`](../skills/blender-project-prescan/)

## 场景

从 SketchUp / CAD 导入出来的工程,常常是**几万个零碎网格**:一把椅子能拆成几十个对象,
整份图纸动辄两万多个。这时候:

1. 打开要等很久,GUI 里大纲树拖一下卡一下;
2. 选中、隐藏、移动一类操作慢到没法连续做;
3. 文件体积也可能虚胖(每个对象都有各自的开销)。

根治办法不是调显示选项,而是**减少对象数量** —— 把**材质相同**的对象物理上拼成一个。

难点也不在"能不能并"(一条 `join()` 的事),而在:

1. 并完之后**世界位姿必须一模一样**(不能有位移漂移 —— 父空间偏移是最常见的坑);
2. **几何不能丢、不能多**(顶点/面数必须严格守恒);
3. UV / 材质分区不能坏;
4. 只有几千个对象、每个几百万顶点的组,耗时才会反直觉地不成比例。

> **这是 [按材质拆分为多个网格体](按材质拆分为多个网格体.md) 的反向操作**,两篇建议对着读。

## 权威依据(先查再做)

### 1. 官方手册原文(Blender 5.2 LTS)

`scene_layout/object/editing/join.html`:

> *"Join merges the selected objects into the active object …
> all selected objects are added into the last selected active object."*

要点:**join 是合并到「活动对象」上**,不是「新建一个」。这就带来两个推论:

* 活动对象的**变换会作用于全体**吗?—— 不会直接作用于几何,但后续残留的非单位缩放会误事,
  所以必须先把**所有对象的世界变换烘焙进几何**(见「机制细节」);
* 活动对象的**材质槽**会被继承给全体 —— 这正是"按材质分组"的意义:同组对象的材质列表必须一致。

### 2. 运行时 API 自省

```python
import bpy
print(hasattr(bpy.ops.object, "join"))          # True
print([p.identifier for p in bpy.ops.object.join.get_rna_type().properties])
```

实测(本工程 24,481 个网格对象)—— **`o.data.users` 全为 1**(详见「前置条件」),
这是能安全合并的前提。

```python
import collections
# mesh 数据块被几个对象共用
users_hist = collections.Counter(o.data.users for o in bpy.data.objects if o.type=='MESH')
# 实测结果:{1: 24481}  ← 无多实例
```

## 机制细节

### 为什么必须先烘焙世界变换

对象的最终位置由三段矩阵连乘决定:

```
世界坐标 = 父.matrix_world × (项.parent_inverse × 项.matrix_world) × 局部坐标
```

而 `join()` 拼接时,只取每个对象的**几何 + 自己的 `matrix_world`** 参与计算。
父级的贡献一旦存在就会被丢掉 —— 表现为**模型以组件为单位散架**。

正确做法是合并前**先解开父子关系,同时把世界变换烧进对象自身的 `matrix_world`**:

```python
bpy.ops.object.parent_clear(type="CLEAR_KEEP_TRANSFORM")
```

这个 `type` 参数是关键 —— **`CLEAR_KEEP_TRANSFORM` 才会保留视觉位置**。
若用 `CLEAR`(默认值),对象会"跳回"自己的局部原点,模型立刻散架。

> ⚠️ 别用 `bpy.ops.object.transform_apply()` 来替代。它会把 scale 应用到几何数据上,
> 在多层父级结构下同样算错,而且会破坏原数据的形状定义。

### 分组键为什么是「材质列表 + UV」

只按"第一个材质名"分组是不够的 —— 多材质槽对象之间也随之可能不同:

```python
key = (tuple(m.name if m else "<空>" for m in o.data.materials),   # 完整材质列表
       tuple(l.name for l in o.data.uv_layers))                    # UV 层名列表
```

UV 必须进 key。实测该工程 **24,408 个网格没有 UV,只有 73 个带 `UVMap`**。
如果把这 73 个和没 UV 的并进同一组,合并结果聚体的 UV 层会被**拉平丢失**。

### 实测分组结果

```
DISTINCT_MATERIAL_SETS = 56          ← 24,481 个对象去重后只剩 56 种材质组合
Top: Color M02]1 独占 24,137 个对象
```

所以最终对象数 = 55 个材质组合 + 1 个排除对象 = **56**(排除项见下)。

## 前置条件(不满足就别合)

**① `mesh.users` 是不是 1 —— v2 起要分两种情况看(见文末「v2 增补」)**

```python
shared = [o for o in meshes if o.data.users > 1]
```

不为 0 说明有多实例(SKP 组件实例 / Alt+D 生成的副本)。两种后果**完全不同**:

| 组的规模 | 后果 | v2 的处理 |
|---|---|---|
| **小-中组**(≤ `ONESHOT_MAX_OBJS`) | 一次性 join 会把一份几何复制 N 份,**文件暴涨** | 走一次性 join;源网格 join 后变孤儿、存盘被丢弃,文件不膨胀 |
| **大组**(> `ONESHOT_MAX_OBJS`) | 走**多段** join 会把该 mesh 的**全部实例几何重复计入**,顶点数直接算错(实测该组本该 1365,变成 16597) | **join 前强制独立化** |

> 若工程整体多实例严重,也可以先把全工程独立化
> ([集合内对象数据独立化](集合内对象数据独立化.md))再合并 ——
> 但那会提前展开全部实例,文件必然变大,自己权衡。

**② 确认可以接受「单体选择能力永久消失」**

合并之后 24,481 个对象名全部消失,**再也选不中单个家具构件**。这是不可逆的,
必须在动手前跟需求方确认粒度:

| 粒度 | 对象数 | 后果 |
|---|---|---|
| 极限(按材质组合) | = 材质组合数 |永远失去单体选择能力 |
| 保留组件层级、组内合并 | 几百~几千 | 仍可选中/移动单个家具 |

**③ 列出不参与合并的对象**

典型如**零厚度平面 + 多分区材质** —— 它靠多个材质分区上色,一旦并进大网格,
分区就跟别的东西混在一起再也摘不出来。

实战中排除的是 `G-物体.24146`:`dimensions.z = 0`,挂着 6 个材质
(`DefaultMaterial / partB / partA / partC / 图层 2 / 图层 3`)。

## 操作方式

### 视口手动(只适合小规模)

选中若干材质相同的对象 → `Ctrl+J`。对象数上了四位数就别手动了,一来点不准,二来会卡住。

### 命令行无头(本主题的主要方式)

> **为什么不用桥 `send.py`**:合并动辄几分钟,桥有 **120s 超时**限制;
> 而且巨型工程本身在 GUI 里就极卡,无头模式绕开了这一步。

```bash
cd <工作目录>
del merge_run.log
blender.exe --background --factory-startup "<源.blend>" ^
            --python merge_by_material.py -- "<输出>_合并.blend"
```

`--factory-startup` 别漏 —— 它会跳过用户插件。实测可省掉加载本机 SketchUp 插件
那个 25 MB `SketchUpAPI.dll` 的开销。

排除名单写在 `<工作目录>\exclude.txt`,一行一个对象名。**名单里的名字若不存在会被告警**
(故意不静默跳过 —— 手抖写错时得知道)。

## 验证

### 三层,缺一不可

**① 合并进程内**:脚本自己比对顶点/面数。

```
CHECK_VERTS 一致
CHECK_POLYS 一致
```

**② 独立复核(必须另开一次 Blender)** —— 「①」只证明内存里的数据对得上,
**不证明存出去的文件还能打开**。

```bash
blender.exe --background --factory-startup "<输出>_合并.blend>" --python verify_merge.py
```

v2 起这一步**零配置** —— 它直接读 `merge_by_material.py` 落盘的 `merge_result.json`,
逐组核对 顶点数 / 面数 / **父级** / **世界包围盒偏差**,外加四项收尾检查
(EMPTY 收敛 / 悬空约束 / 游离对象 / **被引用**的材质与图片数)。

v1 时代(要手工填 `EXPECT_*`)的实测输出:

```
==VERTS 10197620==        ← 与原工程严格相等
==POLYS 7957765==         ← 与原工程严格相等

```

**③ 自测台(日常改动脚本时用)**

20 对象的小场景,核心判据是**世界包围盒最大偏差**:

```

```

0.000000 证明父子 / 旋转 / 缩放全都处理对了。拿 500 MB 工程去试错代价太高,
改脚本逻辑时先跑这个。

## 性能:耗时到底花在哪

总耗时 **5.5 分钟**,分布极其不均:

| 阶段 | 耗时 |
|---|---|
| 加载 510 MB 工程 | ~30 s |
| 世界变换烘焙(24,480 对象) | 2.4 s |
| **第 1 组 `Color M02]1`(24,137 个对象)** | **321.8 s** ← 98% |
| 其余 54 组合计(343 个对象) | 2.7 s |
| 存盘 505 MB | 0.6 s |

### 反直觉的地方

`Am176_048_001` 这组只有 **20 个对象**,却有 **3,326,200 顶点**,合并用了 **0.1 秒**;
而 `Color M02]1` 有 24,137 个对象却只有 542,894 顶点,花了 **321.8 秒**。

**结论:`bpy.ops.object.join` 的开销集中在「对象个数」,跟几何体量关系不大。**
所以估时应该看**最大组有多少对象**,不能用"总对象数 ÷ 总时间"的平均速率外推 ——
我第一次就这么估,得出"还要几十分钟",实际差了两分钟就跑完了。

### 多线程为什么不行

Blender 的 `bpy.data` 不是线程安全的,`join` / `append` 都是**硬性单线程**。
实测开了 32 个线程,3 秒 CPU 增量只有 2.95 秒 —— 只有 1 个核在转。
`--threads` 参数只管渲染和物理模拟,**对数据块操作无效**。

至于"切块并行再拼接":最后那些数据块终究要一个一个灌进同一个 `bpy.data`,
工作量一分不少,收益抵不掉收尾成本。

## 坑(逐条实测)

### 1. 不烘焙世界变换,模型会散架

最高频、后果最严重的一条。见「机制细节」。判据是**世界包围盒偏差 ≈ 0**,
不是"看起来没动" —— 散架往往是组件级别的位置错乱,肉眼在小缩略图上看不出来。

### 2. 前台跑长任务会被 SIGTERM 掐断

跑了一半被杀,日志是空的,磁盘上**没留下任何半成品**,但几分钟白等了。
必须**后台跑 + 独立日志**,脚本里每条日志 `flush` 写盘,随时 `tail`。

### 3. 判断"卡死"要看 CPU 增量,不是日志刷新频率

慢的大组可能在几分钟内**一行新日志都不打**,但它确实在算。
这时候看日志会误判成卡住。正确方法与线程数:

```powershell
$a = (Get-Process blender)[0].TotalProcessorTime.TotalSeconds
Start-Sleep 3
$b = (Get-Process blender)[0].TotalProcessorTime.TotalSeconds
"3秒CPU增量: {0:N2}s" -f ($b-$a)   # > 0.5s = 在干活
```

内存也要注意:实测峰值 2.7 GB(A+B 全在内存时到过 5.15 GB),本机 23.1 GB 无压力,
但小内存机器要先量一下。

### 4. UV 进不了分组键就会被拉平

见「机制细节」。仓库你的工程若全无 UV,这一条可以放松;一旦有一部分是带 UV 的,必检。

### 5. 多个 `.blend` 合并时的「重名」是假警报

两个工程顶层集合名完全撞车(`Collection` / `SKP Imported Data` / `SKP Mesh Objects` 都同名),
22,550 个对象**同名**。但这是 SketchUp 导入器按序号生成
(`G-物体.00001`、`.00002` …)撞出来的,**不代表内容重复**。

别凭名字去重 —— 用**几何指纹**比对:

```python
fp[name] = (tuple(obj.matrix_world.translation), len(me.vertices),
            len(me.polygons), tuple(obj.dimensions))
```

实测:22,550 个同名对象里,**22,549 个指纹不同**(唯一相同的那个是都在原点的空物体)。
所以合并策略应是「**全量并集**」,不是"去重"。

### 6. append 时「以谁为底」影响很大

追加快慢取决于**拉进来多少数据块**,跟底子多大关系不大。
所以要以「对象少的那一边」为底、去追加对象多的那边 —— 实测能省一半时间。

### 7. ast.parse 通过 ≠ 脚本能跑

改造脚本时漏了一行导致 `NameError: argv`。
**语法检查不等于运行时正确**,改完必须实跑(小场景自测台就够了)。

### 8. 合并后文件不一定变小

本次 510.7 MB → 505.2 MB,只瘦了 5.5 MB。因为对象数减少了,但**顶点/面数一个没少**,
而几何数据才是体积主体。想要明显瘦身,还得配合**减面**或**清理孤立数据**。

### 9. 空物体清理要迭代到不动点

删完一批"当前无子级"的 EMPTY 后,会**长出一批新的**无子级 EMPTY。
只删一轮是删不干净的,必须循环直到稳定(本工程 470 → 1)。

## v2 增补(2026-10,实战:541 MB / 50,622 对象 SKP 工程)

上面那套(一次性 join 整组)在**中等规模**工程上工作得很好,但换到一个 5 万对象、
且**大量对象共享同一网格数据块**的工程后,接连踩到四个坑。v2 的加固都从这里来。

### ⑩ 两级 join —— 一次性 join 两千多个对象会崩

```
Calloc array aborted due to integer overflow: len=18446744072358535680x4
in from_uninitialized, total 27960300944     → Blender 直接退出,EXIT=127
```

触发:2405 个对象一次 join(总顶点仅 36 万,却要申请 ~28 GB ⇒ 是 bug 不是真实需求)。
某个数组长度计算**下溢成了负数**(那个 len 按 int64 解释就是 −536870912)。

⇒ **按 ≤ `MAX_BATCH_OBJS`(默认 120)切块,每块做一次性 join 得中间对象,
再把这些中间对象一次性 join 成一个**:

```
2405 个对象 → 21 块 + 第 2 级
363281 顶点与基线完全吻合,偏差 0.000021 ✅
```

⚠️ **绝不能**「逐批 join 到同一个 active」—— 那就是下面这条。

### ⑪ 共享 mesh 数据块 + **多段** join = 几何被重复计入 ★最阴

实测某组 137 个对象,其中 **136 个共用同一份 mesh**(8 顶点):

| 做法 | 结果 |
|---|---|
| 一次性 join 137 个 | **1365 顶点,偏差 0.000003 ✅** |
| 分两批 join(120+17) | **16597 顶点,偏差 1.688313 ❌** |

第二段 join 把该 mesh 在**整个工程里**的全部实例几何都算了进来(多出 15232 = 1904×8)。
**与「选中残留」无关**(加了每批前全场景 DESELECT 后结果一模一样)。

⇒ **正解:join 前先把网格数据独立化**

```python
for o in g:
    if o.data.users > 1:
        o.data = o.data.copy()
```

独立化后:块 2 → 405 顶点、合并后 1365(= 基线)✅

> **代价**:独立化把实例展开成实体,文件会变大。所以 v2 **只在必须走两级 join 的大组**上做。

### ⑫ 选中状态必须【跨组】维护

两级 join 走全局选中路径。若把 `sel = []` 写在**每组内部**,
上一组的存活对象会一直保持选中,被下一组 join 一起吞掉 ——
实测 **67/69 组失败、偏差 5013.98**。

⇒ `sel` 提到循环外;每组开头先取消它;再加一道安全网:

```python
leftover = list(bpy.context.selected_objects)
if leftover:
    bpy.ops.object.select_all(action='DESELECT')
```

> 一次性 join 的快路径用 `temp_override(selected_editable_objects=...)`,
> 不碰全局选中状态,天然免疫 —— 但它处理不了大组,所以两条路径都得留着。

### ⑬ 风险组判定 —— 有些组根本不该碰

| 判据 | 为什么 |
|---|---|
| **跨集合** | 组内对象分散在多个集合 ⇒ 合并会让某个集合凭空多出/失去几何,破坏 SKP 结构 |
| **有成员不在视图层** | 躺在被 exclude 的隐藏集合里 ⇒ join 拿不到它,结果不可预期 |
| `hide_viewport` | 同上 |
| **修改器配置不一致** | join 只保留活动对象的修改器栈,其余成员的全丢,着色会变 |

实测该工程:可合并 393 组里**跳过 24 组(约 1,188 个对象)**,
原因**全部是「有成员不在视图层」** —— 躺在 SketchUp 导入时被 exclude 的隐藏集合
(`组件#89_*66` / `Component#127` 等)。要合并需**先在 Outliner 里取消那些集合的排除**。

### ⑭ excluded 集合还有个静默陷阱

那里的对象 **`matrix_world` 不会被 depsgraph 求值**,停在旧值(往往就是局部坐标)。
任何「算世界包围盒 / 世界坐标」的脚本都会在这拿到错值 ——
**两侧口径都必须限定在视图层内的对象**:

```python
vl_names = {o.name for o in bpy.context.view_layer.objects}
```

顺带:判断「在不在视图层」**必须先物化成 set** —— `o.name not in VL.objects` 是 O(n),
在 5 万对象的视图层上被调用上万次会让脚本卡死几分钟。

### ⑮ 活动对象要挑「带按角度平滑」的

`join()` 只保留**活动对象**的修改器栈。Blender 4.1+/5.x 导入的工程常给每个网格挂
`Smooth by Angle`(按角度平滑,NODES 型)—— 实测该工程 **27,352 / 50,622** 个对象带它。
丢了着色(锐边)就变。

```python
SMOOTH = re.compile(r"按角度平滑|Smooth by Angle")
A = next((o for o in g if any(SMOOTH.search(m.name) for m in o.modifiers)), g[0])
```

### ⑯ 复核口径:别拿「数据块总数」比

存盘时 Blender 会**丢弃 `users == 0` 的孤儿数据块**(材质、图像,旧工程里很常见)。
拿总数比对前后必然误报「丢了材质 / 丢了贴图」。要改成:

```python
sum(1 for m in bpy.data.materials if m.users > 0)
```

### ⑰ 分组键要不要带「父级」

v2 默认带(`GROUP_BY_PARENT = True`)。导入工程的"同类件"往往**按装置分组**——
实测 83 个铜件分布在 19 个不同父级下:

| 口径 | 结果 |
|---|---|
| 只按材质 | 83 → 7(装置归属彻底消失) |
| **材质 + 父级** | **70 → 11**(每组恰好一个装置,可挂回原父级) ← 默认 |
| 材质 + 顶层祖先 | 62 → 21 |

### ⑱ 性能:回答「合并后会更流畅吗」要看四个数

`compare_perf.py <源> <产物>` 同口径跑 `perf_probe.py`。该工程实测:

| 指标 | 源 | 产物 | 含义 |
|---|---|---|---|
| `mesh_objects` | 28,571 | 21,678 | **draw call 代理量** ↓24% |
| `objects_with_mod` | 27,352 | 20,454 | **依赖图求值负担** ↓25% |
| `objsum_verts` | 19,871,278 | 19,871,278 | **每帧真正提交的顶点量,完全不变** |
| `uniq_verts` | 1228 万 | 1627 万 | 显存/内存口径 ↑32.5% |
| 文件体积 | 541 MB | 655 MB | +114 MB |
| 冷启动加载 | 9.0 s | 8.0 s | **反而更快**(受对象数影响 > 文件大小) |

⇒ **会更快,但快在「操作响应」**(选择、移动、改材质、Outliner 浏览、依赖图重算),
**不是「渲染帧率」** —— 每帧提交的顶点数一模一样。
副作用:实例被展开(文件/显存变大),且大对象的**视锥剔除会变差**
(原来能被剔除的小对象,合并后跨越大范围反而剔不掉)。

### 本轮执行结果

393 个候选组 → **369 组成功、0 失败**,最大世界包围盒偏差 **0.000183**(容差 1e-3),
顶点数 / 面数一个不差。对象 50,622 → 43,713;网格对象 28,571 → 21,678。

## 自测台(可复现)

v2 起自测台的场景**逐条覆盖代码路径**,不只验证「能不能合」:

```bash
blender.exe --background --factory-startup --python build_smoke_scene.py
blender.exe --background --factory-startup smoke_scene.blend ^
            --python merge_by_material.py -- "<cwd>\smoke_out.blend" KEEP_ME
blender.exe --background --factory-startup smoke_out.blend --python verify_smoke.py
blender.exe --background --factory-startup smoke_out.blend --python verify_merge.py
```

场景构成:普通组 / 多材质槽 / 带父级的层级 + 旋转缩放 / 一个应被排除的对象,
**外加 v2 的四条新路径**——共享 mesh 的大组(450 个)、独立 mesh 的大组(500 个)、
跨集合的一组、躺在 excluded 集合里的一组。

实测:

```

合并后 11 个(6 组合并 + KEEP_ME + 跨集合 2 + 视图层外 2)
顶点 10225 → 10225   一致
面数 8444 → 8444     一致
共享 mesh 的 450 个大组 → 3600 顶点(= 450×8),几何零重复
CHECK_POSITION OK 最大偏差 0.000002
CHECK_risky_kept_*  OK(被跳过的组原样保留)
```
