# 按材质合并为单个网格体

> 来源: `S:\download\261001\261001x02\261001x02x环境.blend` 实战
> (SketchUp 导入工程:510 MB / 24,481 个网格对象 / 10,197,620 顶点 / 7,957,765 面 / 64 材质)
> 适用: Blender 5.2 LTS
> 脚本包: [`scripts/merge-by-material/`](../scripts/merge-by-material/)
> Skill: [`skills/blender-headless-batch/`](../skills/blender-headless-batch/)

## 场景

从 SketchUp / CAD 导入出来的工程,常常是**几万个零碎网格**:一把椅子能拆成几十个对象,
整份图纸动辄两万多个。这时候:

1. 打开要等很久,GUI 里大纲树拖一下卡一下;
2. 选中、隐藏、移动一类操作慢到没法连续做;
3. 文件体积也可能虚胖(每个对象都有各自的开销)。

根治办法不是调显示选项,而是**减少对象数量** —— 把**材质相同**的对象物理上拼成一个。

难点也不在"能不能并"(一条 `join()` 的事),而在:

1. 并完之后**世界位姿必须一模一样**(不能有位移漂移 —— 父空间偏移是最常见的坑);
2. **几何不能丢、不能多**(顶点/面数必须严格守恒);
3. UV / 材质分区不能坏;
4. 只有几千个对象、每个几百万顶点的组,耗时才会反直觉地不成比例。

> **这是 [按材质拆分为多个网格体](按材质拆分为多个网格体.md) 的反向操作**,两篇建议对着读。

## 权威依据(先查再做)

### 1. 官方手册原文(Blender 5.2 LTS)

`scene_layout/object/editing/join.html`:

> *"Join merges the selected objects into the active object …
> all selected objects are added into the last selected active object."*

要点:**join 是合并到「活动对象」上**,不是「新建一个」。这就带来两个推论:

* 活动对象的**变换会作用于全体**吗?—— 不会直接作用于几何,但后续残留的非单位缩放会误事,
  所以必须先把**所有对象的世界变换烘焙进几何**(见「机制细节」);
* 活动对象的**材质槽**会被继承给全体 —— 这正是"按材质分组"的意义:同组对象的材质列表必须一致。

### 2. 运行时 API 自省

```python
import bpy
print(hasattr(bpy.ops.object, "join"))          # True
print([p.identifier for p in bpy.ops.object.join.get_rna_type().properties])
```

实测(本工程 24,481 个网格对象)—— **`o.data.users` 全为 1**(详见「前置条件」),
这是能安全合并的前提。

```python
import collections
# mesh 数据块被几个对象共用
users_hist = collections.Counter(o.data.users for o in bpy.data.objects if o.type=='MESH')
# 实测结果:{1: 24481}  ← 无多实例
```

## 机制细节

### 为什么必须先烘焙世界变换

对象的最终位置由三段矩阵连乘决定:

```
世界坐标 = 父.matrix_world × (项.parent_inverse × 项.matrix_world) × 局部坐标
```

而 `join()` 拼接时,只取每个对象的**几何 + 自己的 `matrix_world`** 参与计算。
父级的贡献一旦存在就会被丢掉 —— 表现为**模型以组件为单位散架**。

正确做法是合并前**先解开父子关系,同时把世界变换烧进对象自身的 `matrix_world`**:

```python
bpy.ops.object.parent_clear(type="CLEAR_KEEP_TRANSFORM")
```

这个 `type` 参数是关键 —— **`CLEAR_KEEP_TRANSFORM` 才会保留视觉位置**。
若用 `CLEAR`(默认值),对象会"跳回"自己的局部原点,模型立刻散架。

> ⚠️ 别用 `bpy.ops.object.transform_apply()` 来替代。它会把 scale 应用到几何数据上,
> 在多层父级结构下同样算错,而且会破坏原数据的形状定义。

### 分组键为什么是「材质列表 + UV」

只按"第一个材质名"分组是不够的 —— 多材质槽对象之间也随之可能不同:

```python
key = (tuple(m.name if m else "<空>" for m in o.data.materials),   # 完整材质列表
       tuple(l.name for l in o.data.uv_layers))                    # UV 层名列表
```

UV 必须进 key。实测该工程 **24,408 个网格没有 UV,只有 73 个带 `UVMap`**。
如果把这 73 个和没 UV 的并进同一组,合并结果聚体的 UV 层会被**拉平丢失**。

### 实测分组结果

```
DISTINCT_MATERIAL_SETS = 56          ← 24,481 个对象去重后只剩 56 种材质组合
Top: Color M02]1 独占 24,137 个对象
```

所以最终对象数 = 55 个材质组合 + 1 个排除对象 = **56**(排除项见下)。

## 前置条件(不满足就别合)

**① `mesh.users` 必须全为 1(红线)**

```python
shared = [o for o in meshes if o.data.users > 1]
```

不为 0 说明有多实例(SKP 组件实例 / Alt+D 生成的副本)。此时按材质合并会把**同一份几何复制 N 份**,
文件体积暴涨 —— 合并的目的是瘦身,反而变胖就南辕北辙了。

> 若确实有多实例,先做「数据独立化」([集合内对象数据独立化](集合内对象数据独立化.md))再合并。

**② 确认可以接受「单体选择能力永久消失」**

合并之后 24,481 个对象名全部消失,**再也选不中单个家具构件**。这是不可逆的,
必须在动手前跟需求方确认粒度:

| 粒度 | 对象数 | 后果 |
|---|---|---|
| 极限(按材质组合) | = 材质组合数 |永远失去单体选择能力 |
| 保留组件层级、组内合并 | 几百~几千 | 仍可选中/移动单个家具 |

**③ 列出不参与合并的对象**

典型如**零厚度平面 + 多分区材质** —— 它靠多个材质分区上色,一旦并进大网格,
分区就跟别的东西混在一起再也摘不出来。

实战中排除的是 `G-物体.24146`:`dimensions.z = 0`,挂着 6 个材质
(`DefaultMaterial / partB / partA / partC / 图层 2 / 图层 3`)。

## 操作方式

### 视口手动(只适合小规模)

选中若干材质相同的对象 → `Ctrl+J`。对象数上了四位数就别手动了,一来点不准,二来会卡住。

### 命令行无头(本主题的主要方式)

> **为什么不用桥 `send.py`**:合并动辄几分钟,桥有 **120s 超时**限制;
> 而且巨型工程本身在 GUI 里就极卡,无头模式绕开了这一步。

```bash
cd <工作目录>
del merge_run.log
blender.exe --background --factory-startup "<源.blend>" ^
            --python merge_by_material.py -- "<输出>_合并.blend"
```

`--factory-startup` 别漏 —— 它会跳过用户插件。实测可省掉加载本机 SketchUp 插件
那个 25 MB `SketchUpAPI.dll` 的开销。

排除名单写在 `<工作目录>\exclude.txt`,一行一个对象名。**名单里的名字若不存在会被告警**
(故意不静默跳过 —— 手抖写错时得知道)。

## 验证

### 三层,缺一不可

**① 合并进程内**:脚本自己比对顶点/面数。

```
CHECK_VERTS 一致
CHECK_POLYS 一致
```

**② 独立复核(必须另开一次 Blender)** —— 「①」只证明内存里的数据对得上,
**不证明存出去的文件还能打开**。

```bash
blender.exe --background --factory-startup "<输出>_合并.blend>" --python verify_merge.py
```

实测输出:

```

==VERTS 10197620==        ← 与原工程严格相等
==POLYS 7957765==         ← 与原工程严格相等
==MATERIALS 64 | IMAGES 42==   ← 未丢
==TOP_COLLECTIONS ['Collection', 'SKP Imported Data', '相机', 'Export']==
==KEEP_EXCLUDED 保留 OK | 顶点 1067 | 面 1170==
==REOPEN_OK==
```

**③ 自测台(日常改动脚本时用)**

20 对象的小场景,核心判据是**世界包围盒最大偏差**:

```

```

0.000000 证明父子 / 旋转 / 缩放全都处理对了。拿 500 MB 工程去试错代价太高,
改脚本逻辑时先跑这个。

## 性能:耗时到底花在哪

总耗时 **5.5 分钟**,分布极其不均:

| 阶段 | 耗时 |
|---|---|
| 加载 510 MB 工程 | ~30 s |
| 世界变换烘焙(24,480 对象) | 2.4 s |
| **第 1 组 `Color M02]1`(24,137 个对象)** | **321.8 s** ← 98% |
| 其余 54 组合计(343 个对象) | 2.7 s |
| 存盘 505 MB | 0.6 s |

### 反直觉的地方

`Am176_048_001` 这组只有 **20 个对象**,却有 **3,326,200 顶点**,合并用了 **0.1 秒**;
而 `Color M02]1` 有 24,137 个对象却只有 542,894 顶点,花了 **321.8 秒**。

**结论:`bpy.ops.object.join` 的开销集中在「对象个数」,跟几何体量关系不大。**
所以估时应该看**最大组有多少对象**,不能用"总对象数 ÷ 总时间"的平均速率外推 ——
我第一次就这么估,得出"还要几十分钟",实际差了两分钟就跑完了。

### 多线程为什么不行

Blender 的 `bpy.data` 不是线程安全的,`join` / `append` 都是**硬性单线程**。
实测开了 32 个线程,3 秒 CPU 增量只有 2.95 秒 —— 只有 1 个核在转。
`--threads` 参数只管渲染和物理模拟,**对数据块操作无效**。

至于"切块并行再拼接":最后那些数据块终究要一个一个灌进同一个 `bpy.data`,
工作量一分不少,收益抵不掉收尾成本。

## 坑(逐条实测)

### 1. 不烘焙世界变换,模型会散架

最高频、后果最严重的一条。见「机制细节」。判据是**世界包围盒偏差 ≈ 0**,
不是"看起来没动" —— 散架往往是组件级别的位置错乱,肉眼在小缩略图上看不出来。

### 2. 前台跑长任务会被 SIGTERM 掐断

跑了一半被杀,日志是空的,磁盘上**没留下任何半成品**,但几分钟白等了。
必须**后台跑 + 独立日志**,脚本里每条日志 `flush` 写盘,随时 `tail`。

### 3. 判断"卡死"要看 CPU 增量,不是日志刷新频率

慢的大组可能在几分钟内**一行新日志都不打**,但它确实在算。
这时候看日志会误判成卡住。正确方法与线程数:

```powershell
$a = (Get-Process blender)[0].TotalProcessorTime.TotalSeconds
Start-Sleep 3
$b = (Get-Process blender)[0].TotalProcessorTime.TotalSeconds
"3秒CPU增量: {0:N2}s" -f ($b-$a)   # > 0.5s = 在干活
```

内存也要注意:实测峰值 2.7 GB(A+B 全在内存时到过 5.15 GB),本机 23.1 GB 无压力,
但小内存机器要先量一下。

### 4. UV 进不了分组键就会被拉平

见「机制细节」。仓库你的工程若全无 UV,这一条可以放松;一旦有一部分是带 UV 的,必检。

### 5. 多个 `.blend` 合并时的「重名」是假警报

两个工程顶层集合名完全撞车(`Collection` / `SKP Imported Data` / `SKP Mesh Objects` 都同名),
22,550 个对象**同名**。但这是 SketchUp 导入器按序号生成
(`G-物体.00001`、`.00002` …)撞出来的,**不代表内容重复**。

别凭名字去重 —— 用**几何指纹**比对:

```python
fp[name] = (tuple(obj.matrix_world.translation), len(me.vertices),
            len(me.polygons), tuple(obj.dimensions))
```

实测:22,550 个同名对象里,**22,549 个指纹不同**(唯一相同的那个是都在原点的空物体)。
所以合并策略应是「**全量并集**」,不是"去重"。

### 6. append 时「以谁为底」影响很大

追加快慢取决于**拉进来多少数据块**,跟底子多大关系不大。
所以要以「对象少的那一边」为底、去追加对象多的那边 —— 实测能省一半时间。

### 7. ast.parse 通过 ≠ 脚本能跑

改造脚本时漏了一行导致 `NameError: argv`。
**语法检查不等于运行时正确**,改完必须实跑(小场景自测台就够了)。

### 8. 合并后文件不一定变小

本次 510.7 MB → 505.2 MB,只瘦了 5.5 MB。因为对象数减少了,但**顶点/面数一个没少**,
而几何数据才是体积主体。想要明显瘦身,还得配合**减面**或**清理孤立数据**。

### 9. 空物体清理要迭代到不动点

删完一批"当前无子级"的 EMPTY 后,会**长出一批新的**无子级 EMPTY。
只删一轮是删不干净的,必须循环直到稳定(本工程 470 → 1)。
