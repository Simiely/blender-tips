# 覆盖区框选批量删除对象（俯视 Z 轴）

> 关联：Skill [`blender-region-batch-delete`](../skills/blender-region-batch-delete/) / 脚本包 [`scripts/region-batch-delete/`](../scripts/region-batch-delete/)
>
> 通道：**不开 GUI**，走 `blender.exe --background <工程> --python <脚本>`（与 [主题 43](按材质合并为单个网格体.md) / [主题 44](追加合并两个工程.md) 同一条命令行通道，不是 9877 桥）。

## 场景

导入型工程对象数爆炸（本案例 **320,474** 个），只想保留某个区域、把其余清掉。用户已经在工程里放好**两个网格体当"区域标记"**（名字里带「Z轴覆盖范围」），要求：

> 从 Z 轴上方往下看（俯视），**被这两个网格体包住的对象全部删除**。

这类需求在 GUI 里几乎做不动 —— 32 万对象的选择、框选、删除都会卡死，而且"框选"本身受视图透视与遮挡影响。必须走无头脚本。

## 一句话做法

**"俯视 Z 轴"= 忽略 Z 轴**，判定退化成**世界 XY 平面上的二维矩形包含**：

```
对象被删除  ⟺  它的世界 XY 包围矩形「完全落在」两个标记矩形之并集内
```

再用**精确矩形包含判据**（面积容斥，不是采样、不是射线、不是缩小包围盒）一次性算准名单 —— 干跑 4.36 s 出结果，实测 2D 口径与 3D 口径（叠加 Z 带）**答案完全一致**（都是 143,318）。

## 一、判定算法

### 1. 标记体 → 世界 XY 矩形

```python
def wbbox(mw, bb):
    xs, ys = [], []
    for c in bb:                       # bb = 对象局部 bound_box 的 8 个角
        xs.append(mw[0][0]*c[0] + mw[0][1]*c[1] + mw[0][2]*c[2] + mw[0][3])
        ys.append(mw[1][0]*c[0] + mw[1][1]*c[1] + mw[1][2]*c[2] + mw[1][3])
    return (min(xs), min(ys), max(xs), max(ys))
```

按 **`matrix_world` 的前两行**直接展开叉乘，**不构造 `Vector`、不调 `matrix_world @ Vector(...)`**。
32 万对象 × 8 角 ≈ 256 万次变换，省掉对象分配后整个干跑只要几秒。

### 2. 完全包含判据：并集格网

两块标记是**并集**（不是一个大矩形），不能拆成"在 R1 里 **或** 在 R2 里"逐条判 —— 那样会把"横跨两块、中间悬空"的对象误判成在内。正解：

```
area(R ∩ 并集) == area(R)      ⇒ 完全包含
```

`area(R ∩ 并集)` 用**格网分解**精确求：取所有矩形边界的 x/y 坐标把平面切成互不重叠的格子，轴对齐矩形必然由若干**整格**组成，于是"整格在内 / 整格在外"必然成立，逐格求交面积求和即可。

对 2 块矩形，这等价于容斥式 `area(R∩R1) + area(R∩R2) − area(R∩R1∩R2)`（交集矩形 = `max`/`min` 各取一次）；格网写法对 **N 块任意形状的并集都精确**，不会漏高阶容斥项。容差取 `1e-6 × max(1, w*h)` 相对量，别用绝对值（这个工程的坐标量级到 1e6）。

### 3. 退化矩形：零宽或零高必须走四角点

`EMPTY`、`CAMERA`、`LIGHT`、点数据对象的 `bound_box` 是**零尺寸**（8 个角重合或退化成一条线）⇒ `w*h = 0`，面积判据两侧恒等，**任何位置都会判成"包含"**。必须单独分流：

```python
if w <= 1e-9 or h <= 1e-9:
    return pin(x0,y0) and pin(x1,y0) and pin(x0,y1) and pin(x1,y1)   # 四点都在并集内
```

本案例里这类"零尺寸对象"有 **5,946 个 EMPTY + 14 个 CAMERA**，全部按四角判定落到"在区内"——用面积判据会把**整个工程的所有空物体与相机都删掉**。

### 4. 父级塌陷：删父级会带走外面的子级

被删对象里有 **256 个是"外部对象"的父级**（挂在外面的子级共 **485** 个）。直接删，这些子级会跟着父级一起消失 —— 或者在世界里瞬移（父级变换没了，子级按自身局部坐标重新落位）。

**做法：删除前先"冻结"这批"父级在内、自己在外"的子级**（即 Clear Parent Keep Transform）：

```python
mw = o.matrix_world.copy()
o.parent = None
o.matrix_parent_inverse.identity()
o.matrix_world = mw          # 世界变换逐位不变
```

### 5. 分块删除 + 计数硬闸

```python
CHUNK = 10000
for i in range(0, tot, CHUNK):
    bpy.data.batch_remove(victims[i:i + CHUNK])
```

干跑数与执行前**必须重新数一遍**，不一致就 `raise SystemExit` —— 这是防"名单算错还在真工程上动手"的唯一一道闸。

## 二、性能真相（本案例实测，反直觉）

**在这类超大规模工程里，每个对象的删除成本是 ~20 ms 级，而且几乎与"你用哪种 API"无关。**

| 方法 | 单对象耗时 | 规模 143,318 推算 |
|---|---|---|
| `bpy.data.objects.remove(o, do_unlink=True)` | **123.6 ms** | 4.9 小时 |
| `o.unlink(...)`（从集合摘除） | 26.6 ms | 1.06 小时 |
| `bpy.ops.object.delete()`（批选后删） | 44.2 ms | 1.76 小时 |
| **`bpy.data.batch_remove(list)`** | **23.0 ms** | **0.92 小时** |
| `remove(do_id_user=False, do_ui_user=False)` | 135.6 ms | —— 没有收益 |

- **`batch_remove` 是实测最快**（官方文档原话是"更快，但不如逐个 `remove()` 安全灵活"）。终选它。
- **换参数救不了**：`do_id_user` / `do_ui_user` 置 `False` **一分钱不省**（135.6 ms，反而更慢）。
- **视图层大小无关**：先在视图层里排除掉 3 个顶层集合、视图层对象从 254,734 变化，**单对象耗时纹丝不动**。
- **集合大小无关**：把小集合里的对象单独删，照样 20 ms+。
- **行为解释**：读操作（`bound_box`、`matrix_world`）是廉价的；**每一次"写"操作**都触发 Blender 的 ID 记账 / 视图层同步 / 依赖图重算，这个代价在超大 `bpy.data` 下被放大成 ~20 ms 的固定开销。

逐个删除 vs `batch_remove` 的差别不在"每对象成本"，而在**每对象触发一次还是每批触发一次**。

## 三、坑（按严重度）

1. **★ `bound_box` 永远是局部坐标** —— 必须过 `matrix_world`。用局部 AABB 直接比矩形，等于假设所有对象都躺在原点，结果毫无意义。
2. **★ 零尺寸对象要用四角点判定**（见 §1.3）—— 面积判据对它们恒真，会误删**全工程所有空物体与相机**。
3. **★ 父级塌陷**（见 §1.4）—— 本案例 256 个受害父级带 485 个子级，不冻结就是"外面也少东西"。
4. **★ 循环里绝不要 `bpy.data.objects.get(name)` / 按名字查对象** —— 在 32 万规模下病态慢（早期版本因此挂死 10 分钟以上）。要判成员关系就**自己建 `set`**；要遍历就 `list(bpy.data.objects)` 一次拿快照。
5. **★ 删除后不能碰旧引用** —— `batch_remove` 之后任何残留的 `o.name` 都会抛 `ReferenceError: StructRNA of type Object has been removed`。需要用到的字段必须在删除**前**冻结成纯值。
6. **★ 另存后对象数会少 1** —— 内存内 `len(bpy.data.objects)` = **177,156**，另存后重开 = **177,155**。少掉的是**零用户（`users == 0`）且无 fake user 的数据块**，Blender 存盘时本就不写它（同批还丢掉 1 个 mesh、35 个 image）。这不是删除逻辑出错，是存盘语义 —— 但**必须知道**，否则复核时会以为丢了一个对象。
7. **★ 干跑与执行必须是同一套数学** —— 复制两份判据代码，改一处忘另一处，就会出现"算 143,318、删 143,317"这种最难查的偏差。两处代码逐字节同源，或干脆抽成一个 `region_geom.py`。
8. **孤儿清理用 `orphans_purge(do_recursive=True)`** 会把范围滚得很大、很慢（本案例全量一遍 **42.7 s / 2,214 个**）；`do_recursive=False` 连跑两遍（pass1 → 822、pass2 → 64，共 0.6 s）就够了。
9. **`bpy.data.batch_remove` 的清单要一次性建好** —— 边遍历边删 / 边删边取引用，几乎必然踩到第 5 条。

## 五、复核清单（另起一个脚本，重开新文件）

1. **区内残留 = 0** —— 用**同一套判据**在**新文件**上重算一遍"完全在区内"的对象数，判据是 **0**（不是"变少了"）。
2. **对象数** —— 重开计数与"内存内计数 − 存盘丢弃"对得上（本案例 177,155 vs 177,156，差 1 且能解释）。
3. **类型分布 / 数据块计数** —— 全部列出，供人工比对。
4. **场景包围盒** —— 逐位读一遍，确认没有整块区域消失导致的异常收缩。
5. **区内残留按类型** —— 非零时按类型分组打印，能立刻看出是哪一类判据写错了（例如只剩 EMPTY ⇒ 退化矩形分支漏了）。
