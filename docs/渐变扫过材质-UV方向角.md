# 渐变扫过材质 · UV 方向角

平面上的**黑白渐变宽带横扫**：一条（或多条）亮带沿指定方向扫过去、无缝循环。
**扫过方向是一个 0–360° 的 UV 平面角度**（0° 沿 +U、90° 沿 +V、180° 就是反向），
**坐标源就是网格体自己的 UV 层**（`坐标_纹理.UV`，不是包围盒归一化的 `Generated`），
所有参数都长在一个**空对象**上（材质可整体搬到别的网格体），
渐变本身交给 **ColorRamp** —— 波形结构归脚本，颜色归手调。

- 脚本包：[`../scripts/sweep-angle-material/`](../scripts/sweep-angle-material/)
- AI 作业规范：[`../skills/blender-sweep-angle-material/`](../skills/blender-sweep-angle-material/)

---

## 1. 场景

实际需求（逐条递进，最终形态就是本主题）：

1. 「在这个平面上做**渐变扫过**的动态，渐变最好用**颜色渐变**来做，方便我自己修改，扫过的**速度用驱动控制**」
2. 「渐变色就是**黑白**渐变就可以了」
3. 「再加一层**水平方向的渐变**叠加，水平方向是**固定不动**的，两个效果可以合成 —— **如果水平方向用白色，就不会影响竖直方向的效果**」
4. 「驱动控制可以是**一个空对象**吗？这样我的材质就方便用到别的网格体上」
5. 「扫过方向我觉得应该是 **0–360**，这样自由度更高，改名叫**扫过角度**；**0° 就对应现在的 1**」
6. 「0–360 就是**从 UV 的角度**来说的」
7. 「**不需要常驻面板**」（→ 参数只挂在空对象上，不做 N 侧栏面板）
8. 「你现在这个**节点没有接 UV** 呢，需要调整」（→ 坐标源从 `Generated` 换成 `坐标_纹理.UV`，见 §2.8）

一句话：**一层会扫的 + 一层不动的，相乘合成；扫的方向可以按 UV 角度自由转；坐标源走网格体自己的 UV；所有旋钮在空对象上；颜色留给 ColorRamp。**

## 2. 做法

### 2.1 锚点：空对象「渐变控制」= 参数载体

```
depsgraph 依赖： 驱动器 ──SINGLE_PROP──> 空对象「渐变控制」的 5 个自定义属性
                 材质节点树 ── 与网格体解耦，可整体挂到别的 mesh 上
```

- 空对象用 `D.objects.new(name, None)` 建（`None` ⇒ EMPTY，不动用 operator）；
  `empty_display_type='CUBE'`、`empty_display_size=1.6`、`hide_render=True`。
- **★ 交付给用户时必须把它设成活动对象**，否则用户「找不到驱动控制参数」（见坑 4）。
- 旋钮用 `id_properties_ui(name).update(description=..., min=..., soft_max=...)` 补上描述与滑杆范围
  （键名即显示名，中文键直接显示中文）。

### 2.2 节点管线

```
纹理坐标(UV) → 分离XYZ
二维方向投影 t = (u·cosθ + v·sinθ) / (|cosθ| + |sinθ|)       ★ 见 §2.3
  → ×条数 → −相位 → FLOORED_MODULO 1 → 颜色渐变_扫过 ─┐
分离XYZ.Y → ×水平条数 → FLOORED_MODULO 1 → 颜色渐变_水平 ─┤
                              混合(RGBA, MULTIPLY, Factor=1.0) ─┴→ 原理化BSDF
                                                        ├─ Base Color
                                                        ├─ Emission Color
                                                        └─ Emission Strength ← 发光强度
相位 = 扫过速度 × (frame − 1) / fps                    ★ Value 节点输出 + SCRIPTED 驱动
```

- 节点 **21** / 连线 **23** / 驱动 **6**（相位、角度_余弦、角度_正弦、条数、水平条数、发光强度）。
- **坐标源 = `坐标_纹理.UV`**（见 §2.8）。整条链只读 `分离_XY` 的 X / Y，
  所以换坐标源就是**换这一根线**，下游一个字都不用改。

### 2.8 ★ 坐标源：`UV` 还是 `Generated`（换一根线的差别）

`分离_XY.Vector` 接哪个插座，决定了图案"长在什么坐标上"：

| 坐标源 | 含义 | 什么时候用 |
|---|---|---|
| **`UV`（默认）** | 网格体自己的**渲染活动 UV 层** | 材质要**换成别的网格体**时，图案跟着那个网格自己的 UV 走（不要求包围盒一致）。**要求目标网格体有 UV 层** |
| `Generated` | 按**物体包围盒**归一化的局部坐标 | 不想要求用户先展 UV；或网格体压根没有 UV 层 |

切换就是一行（脚本里对应顶部常量 `COORD_SOURCE`）：

```python
old = next(l for l in nt.links
           if l.to_node.name == "分离_XY" and l.to_socket.name == "Vector")
dst = old.to_socket                      # ★ 先把目标插座抓在手里
nt.links.remove(old)
nt.links.new(nt.nodes["坐标_纹理"].outputs["UV"], dst)   # 或 "Generated"
```

**两个必须知道的事实**：

1. ★ **`UV` 插座给的是「渲染活动 UV 层」**，不是"名字叫 UVMap 的那层"。网格体可以有多层 UV，
   渲染用哪层由该层的 `active_render` 标记决定。没有 UV 层时它返回**全 0** ——
   不是报错，是**静默坏掉**（图案整个塌成一种颜色）。所以 `build_sweep_angle.py` 在
   `COORD_SOURCE="UV"` 时会**先断言目标网格体有 UV 层**。
2. ★★ **对一块平整、UV 恰好是 0–1 正投影的网格体，`UV` 与 `Generated` 的渲染结果逐像素相同。**
   实测（256×256，四个角度逐一比对）：最大差 **0.00392157**，**恰好 = 1/255 一个 8bit 量化步**，
   且只有 **1~3 个分量**（共 262144）不同、平均差 **≈1e-8**。
   ⇒ **"坐标源到底接的是哪一个"光看画面是分不出来的**，结构断言也只能证明"线接在 UV 插座上"，
   证明不了"求值真的走了 UV"。要证它，**必须扰动 UV**（见 §3.12）。

### 2.3 ★★ 方向 = UV 平面内的角度投影（本主题的核心）

原来"方向"只能取 ±1（正扫 / 反扫），因为扫过坐标是**一维**的 —— 直接取 `分离_XY.X`。
把它升级成任意角度，正解不是"给一维量乘个系数"，而是**把二维坐标投影到角度方向上**：

```
t(θ) = (u·cosθ + v·sinθ) / (|cosθ| + |sinθ|)
```

- **θ = 0°** → `t ≡ u` ⇒ **与"直接取 X"逐点相同**（这是"0° 就对应原来的 1"的严格含义，不是近似）；
- **θ = 90°** → `t ≡ v`，沿 V 扫；
- **θ = 180°** → `t ≡ −u`，等价原来的 `−1`（反向）；任意中间角 = 斜扫；360° 回到起点。
- 负值不用管：下游是 `FLOORED_MODULO`，负 t 照样循环（这也是当初必须用 `FLOORED_MODULO`
  而不是普通 `MODULO` 的同一个理由）。

落地成三个数学节点（放在 `数学_倍频` 左侧，读图是左→右）：

| 节点 | 类型 | 作用 |
|---|---|---|
| `角度_余弦` | Value (+SCRIPTED 驱动) | `cos(radians(ang)) / (|cos|+|sin|)` |
| `角度_正弦` | Value (+SCRIPTED 驱动) | `sin(radians(ang)) / (|cos|+|sin|)` |
| `数学_方向X` / `数学_方向Y` | Math MULTIPLY | `u × 余弦` / `v × 正弦` |
| `数学_投影` | Math ADD | 两者相加 → 接 `数学_倍频` 原来那个输入 |

- 接线时**别硬写 `数学_倍频.inputs[0]`**：MULTIPLY 有**两个同名 `Value` 输入**、而且
  `NodeSocket` 在 5.2 **没有 `.index`**。正确做法是**从旧连线上取**：遍历 `nt.links` 找到
  `分离_XY.X → 数学_倍频` 那条，先把它的 `to_socket` 抓在手里，再删连线、把 `数学_投影` 接回**同一个插座**。
- θ 取偶数个 90° 时 `|cos|+|sin| = 1`，归一化分支退化为恒等；只有在斜角才起作用。

### 2.4 归一化分母：让「条数」不随角度变

`u, v ∈ [0,1]`，所以 `u·cosθ + v·sinθ` 的值域宽度是 **`|cosθ| + |sinθ|`** ——
θ=45° 时是 **√2**。不除这个分母，把角度从 0° 拨到 45°，**条纹会凭空多出 1.41 倍**、
「条数」在不同角度含义不一致（用户会以为材质坏了）。

除以 `(|cosθ| + |sinθ|)` 之后 t 的值域**恒为宽度 1** ⇒ 「条数」在任何角度都表示"整块平面上有几条"。
代价是斜角时条纹在世界空间里略宽 —— 这是**刻意的取舍**（参数语义稳定 > 绝对物理宽度）。

### 2.5 乘性合成：水平层全白 = 中性（逐像素实测）

用 `ShaderNodeMix`（`data_type='RGBA'`, `blend_type='MULTIPLY'`, **`Factor=1.0`**）：

| 水平层色标 | 实测（正交俯视渲染，逐像素比对） |
|---|---|
| 全白 + `Factor=1` | 与 **`Factor=0`（数学上 = 直接连接）** 最大差 **0.00392**、平均差 **0.000000** ⇒ **等价** |
| 黑白条 + `Factor=1` | 与"纯扫过"最大差 **0.816**、平均差 **0.133** ⇒ **叠加确实生效** |

⇒ 用户的保底方案成立：**水平层只要给全白，就等于没接**；想加静态水平条就调它的色标，不用改接线。

- **★ `Factor=0` 不是"纯相乘"**：MULTIPLY 模式下 Fac=0 会退化成**只取 A**（等于直接把扫过接出去）。
  要"相乘"必须是 **Fac = 1.0**。这个坑很容易踩，因为 A/B/Fac 三个旋钮看起来对称。
- 想彻底旁路水平层，也可以直接把 `颜色渐变_扫过.Color` 接到 BSDF（跳过混合节点）—— 但**留着节点更方便**。

### 2.6 ColorRamp 只管颜色（给用户留手调口）

- 结构（条数 / 相位 / 循环）全在 Math 域，**ColorRamp 上不挂任何驱动**，用户随时双击改色标。
- 出厂给 3 档黑/白/黑、`interpolation='EASE'`；用户实测改成 **7 档**（黑/白交替 ⇒ 3 条亮带）也完全正常。
- **`ColorRamp` 的输入插槽叫 `Factor`，不是 `Fac`**（5.2 实测：`inputs = [(0,'Factor')]`）。
  `Fac` 是老的 `ShaderNodeMixRGB` 才有的名字。
- **`ColorRamp` 的元素数不能少于 2**（RNA 强制下限），所以"删到只剩一个"做不到；
  新建节点自带 2 个，写色标前先补齐再赋值。

### 2.7 参数表（5 个滑块，键在 `渐变控制` 空对象上）

| 键 | 类型 | 默认 | 环 | 说明 |
|---|---|---|---|---|
| `扫过速度` | float | 0.2 | min 0 / soft_max 5 | 周期/秒；0 = 静止；负值 = 反向 |
| `扫过角度` | float | 0.0 | min 0 / soft_max 360 | **UV 平面角度（度）**。0°=沿 +U（=原来的 1）、90°=沿 +V、180°=反向 |
| `扫过条数` | float | 1.0 | min 1 / soft_max 20 | 扫过方向上同时存在的渐变条数 |
| `水平条数` | float | 1.0 | min 1 / soft_max 20 | 静态水平层（沿 V）的条数；水平层全白时无影响 |
| `发光强度` | float | 2.0 | min 0 / soft_max 20 | 合成后的整体发光强度 |

> 参数键是**中文键名**，`id_properties_ui` 里 `min/max` 是**硬边界**、`soft_min/soft_max` 是**滑杆范围**。
> 本例故意**只给 soft_max=360 不给硬 max** ⇒ 滑杆看着是 0–360，想输 400（多转一点）也不会被夹住。

## 3. 坑（全部实测）

### 3.1 ★★ 改完自定义属性，只调 `view_layer.update()` 读不到新值

```python
ctrl["扫过角度"] = 45.0
bpy.context.view_layer.update()
nt = mat.node_tree
print(nt.nodes["角度_余弦"].outputs[0].default_value)   # ← 读到的是旧值！(1.0)
```

**必须**额外标脏，节点树上的驱动器才会重算：

```python
ctrl.update_tag()                 # 参数所在 ID
nt.update_tag()                   # 驱动器所在 ID(节点树)
bpy.context.evaluated_depsgraph_get().update()
```

- 实测对照：只 `view_layer.update()` ⇒ 插座值**不动**；`ctrl.update_tag()` / `nt.update_tag()` /
  `mat.update_tag()` / `dg.update()` / 帧号撞一下 —— 任一种 ⇒ **立刻跟上**。
- **GUI 里用户拖滑杆是会自动打 tag 的**，所以这个坑只在**脚本里**出现；
  但脚本读了陈旧值会得出**完全错误的结论**（本主题在开发中因此一度误判
  "`cos/radians/abs` 不在驱动表达式白名单里""驱动器坏了"，白写了一圈探针）。
- 推论：**`driver.is_valid` 也是这个刷新之后才可信**。在刷新之前读，新建的驱动器会显示
  `is_valid=False` —— 那是**初始值还没算**，不代表它坏了。

### 3.2 ★★ 拿"临时材质"探驱动器 = 无效实验

在 `bpy.data.materials.new()` 造的一次性材质上挂驱动器 `SINGLE_PROP`（指向真实空对象的属性），
打印 `is_valid` 与求值结果 —— **全是假的**：材质**没被任何物体使用** ⇒ 它不在依赖图里 ⇒ **驱动器根本不求值**。

实测：13 个候选表达式**全部**显示 `is_valid=True`、**求值全部 `0.0`**
（连 `pi` 都返回 `0.0`，应该是 3.14159；`frame` 也返回 `0.0`，应该是帧号）。
如果信了这次探测，会得出"所有写法都合法"的结论 —— 恰好这次结论蒙对了，但**方法是错的**。

**正解**：要探就在**正在被使用**的材质/对象上探，或者干脆用**行为法**（改属性 → 强刷新 → 看值变没变）。

### 3.3 `driver.expression` 对非 SCRIPTED 类型是**自动生成的显示串**

`AVERAGE` / `SUM` 等类型的 `driver.expression` 会显示成**字面量**，看起来像"忽略了变量"：

```
条数      AVERAGE   expr='0.5'     ← 而 扫过条数 = 1.0（求值实测 = 1.0，完全正确）
水平条数   AVERAGE   expr='3.765'   ← 而 水平条数 = 2.0
发光强度   AVERAGE   expr='1.0'     ← 而 发光强度 = 2.0
```

这些串是 Blender 自己生成的显示文本，**不是求值依据**。**别用 `expression` 字段判断对错**，
要用「求值后的插座值 == 旋钮值」来判断。

### 3.4 ★ 参数挂在空对象上 ⇒ 必须把该对象设为活动对象

Blender 的**物体属性面板只显示活动对象**。只 `select_set(True)` 是不够的 ——
用户选中了空对象、面板里却显示的是"平面"（上面已经没有自定义属性了）⇒ **"我找不到驱动控制参数"**。

```python
for o in C.view_layer.objects: o.select_set(False)
ctrl.select_set(True)
C.view_layer.objects.active = ctrl          # ★ 这一行才是关键
```

### 3.5 改驱动器的**变量**必须原子重建

只想把 `dir` 变量换成 `ang` 时，直接删掉一个变量再加一个新的 ⇒ 整条驱动会卡在
`is_valid=False`、数值**冻结在旧值**上（连强制求值都不刷）。

**正解：整条删掉重建**（`ad.drivers.remove(fc)` → `sock.driver_add("default_value")` → 重新配），
改变量表就会强制重新编译表达式。删之前记得把要用的字段**先冻结成局部变量**
（`data_path` / `v.name`），删完再读会 `ReferenceError: StructRNA ... has been removed`。

### 3.6 `SINGLE_PROP` 变量的赋值顺序

```python
t = var.targets[0]
t.id_type = 'OBJECT'        # ★ 必须先设 id_type
t.id = ctrl                 # ★ 再设 id（5.2：顺序反了会被拒/落到 None）
t.data_path = '["扫过角度"]'
```

另外：写"补充参数"的循环时，`for prop, var_name in SPEC` 的**顺序别反**。
反了会造出一堆**指向不存在属性**的悬空变量 —— 它们**不会报错**，但 `AVERAGE` 型驱动器会把
每个悬空变量当 `0` 平均进去 ⇒ **数值正好变成一半**（实测：`扫过条数` 1.0→0.5、`水平条数` 7.53→3.765）。

### 3.7 `FLOORED_MODULO`，不是 `MODULO`

扫过相位会走负值（尤其 θ=180° 时 `t = −u`）。普通 `MODULO` 对负值**裁剪** ⇒ 条纹在边界断掉。
`FLOORED_MODULO`（地板取模）才对负值给出 `[0,1)` 的正确结果 —— 无缝循环靠它。

### 3.8 零碎的 API 事实

| 事实 | 说明 |
|---|---|
| `ColorRamp` 输入插座名 = **`Factor`** | 不是 `Fac`（那是 `ShaderNodeMixRGB` 的） |
| `ColorRamp` 元素数 ≥ **2** | RNA 硬下限，"删到只剩一个"做不到 |
| `ShaderNodeTree` **没有** `.update()` | 5.2 实测 `AttributeError` |
| `NodeSocket` **没有** `.index` | 在 5.2 的 `NodeSocketVector`/`NodeSocketFloat` 上都不存在；插座只能**按 `(name, type)` 配**或从连线上取 |
| `bpy_prop_collection.__contains__` 只收字符串 | `a_node in nt.nodes` 会 `TypeError`，要写 `a_node.name not in nt.nodes` |
| RNA 包装对象**不能比 `is`** | `l.from_node is a_node` 会是 `False`；比 `.name` |
| `Text.use_register` **不存在** | 5.2 没有这个属性（想"重开自动跑"只能走别的路；本轮用户也明确**不要常驻面板**） |
| 节点布局改完别碰 `nt.update()` | 不存在；要重画靠 GUI |

### 3.9 生成 HTML 时别用 `%` 格式化

预览 HTML 里的 CSS 有 `width:100%` / `minmax(240px,1fr)` 这类 `%`，
用 `"...%s..." % (...)` 拼会炸：`ValueError: unsupported format character ';' (0x3b) at index 588`。
用 `__PLACEHOLDER__` + `str.replace`。

### 3.10 拿渲染做验收时：**朝向类** shader 用梯度比，不要用"亮度质心"

测"条纹是竖的还是横的"最稳的读数 = 正交俯视渲染后算两个方向的平均绝对梯度：

| 角度 | `gradX / gradY` | 含义 |
|---|---|---|
| 0° | **10.51** | ≫1 ⇒ 竖条（沿 U 变化） |
| 45° | **1.000** | ≈1 ⇒ 斜条（各向同性） |
| 90° | **0.096** | ≪1 ⇒ 横条（沿 V 变化） |
| 180° | **10.50** | 竖条，且逐像素就是 0° 的左右镜像（见 §4） |

（不要用"亮度质心"：AgX 的高位平台会把质心拉平，实测质心 0.5→0.57→0.57→0.55→0.53 完全读不出位移；
要用"两个半高交点的中点"或者干脆像本例一样用**梯度比**。）

### 3.11 ★★ 拿剖面做核验时，两个"自证式"陷阱（本轮实测踩过）

**陷阱 A：沿 t 的剖面必须先按 1.0 取模再分箱。**
θ > 90° 时 `t` 是**负数**（180° 就是 `t = −u`）。天真的分箱写法

```python
t = (u * cs + v * sn) * k
bi = int(t * bins)
if 0 <= bi < bins:        # ← 180° 时绝大多数点在这被丢掉
    ...
```

会把 180° 的剖面几乎清空：**"条数"塌成 1**、任何相关系数退化成 0。
实测读数长这样 —— 看起来像"材质在 180° 坏了"，其实是**度量写错了**：

```
180 °  ... 沿 t 条数=1          ← 假象
四角度沿 t 的条数 = [4, 4, 4, 1]
[FAIL] ★ 归一化成立
0° vs 180° 剖面:同向相关=+0.0038  镜像相关=-0.0062
```

正解：`t = (((u * cs + v * sn) * k)) % 1.0`。**这和材质自身用的 `FLOORED_MODULO 1.0` 是同构的**，
而且因为图案本身就是周期 1 的，接缝处**连续**，不会引入假跳变边。

**陷阱 B：不要拿「沿 t 的剖面」验证"180° 是 0° 的镜像"——那是自证。**
`profile_t` 的**采样方向本身就跟着 t 翻**（180° 时 bin `b` 采的是 `x ≈ (1−b/bins)·W` 处的像素），
所以 0° 与 180° 的 t 剖面**天生重合**；再手工 `[::-1]` 翻一次等于翻了两次 ⇒ 变成反相关：

```
0° vs 180° 剖面:同向相关=+1.0000  镜像相关=-0.3014     ← 全是度量的锅
```

**正解：直接比像素。** 平均 `|I180(x,y) − I0(w−1−x,y)|`（镜像）应 ≪ 平均 `|I180(x,y) − I0(x,y)|`（同向）：

```
平均逐像素差:同向 0.273658 / 镜像 0.001884 / 0° 图自身左右不对称度 0.273729
[PASS] 可证伪前提:0° 图本身左右强不对称(0.273729 ≫ 0.001884)⇒ 镜像判据不会自动成立
[PASS] 180° = 0° 的左右镜像(镜像差 0.001884 ≪ 同向差 0.273658,小 145 倍)
```

> 教训：**"能失败的判据"才算判据。** 顺手把「图案自身左右不对称度」也量出来（≈0.2737），
> 才能证明这个镜像判据不是恒真的 —— 否则一个左右对称的图案会让"镜像 = 同向"两边都成立，测了等于没测。

### 3.12 ★★ 第三个自证陷阱：**渲染分不出坐标源换没换**

把坐标源从 `Generated` 换成 `UV` 之后，四角度渲出来是这样的：

```
0   ° gradX=0.01971 gradY=0.00188 比值= 10.510     ← 改前(Generated)也是 10.510
45  ° gradX=0.01004 gradY=0.01004 比值=  1.000     ← 改前也是 1.000
90  ° gradX=0.00190 gradY=0.01971 比值=  0.096     ← 改前也是 0.096
180 ° gradX=0.01980 gradY=0.00189 比值= 10.502     ← 改前也是 10.502
```

**一模一样。** 逐像素比对新旧两版渲染：

| 角度 | 最大差 | 平均差 | 超过 1e-6 的分量数 |
|---|---|---|---|
| 0° | 0.00392157 | 0.00000001 | **1** / 262144 |
| 45° | 0.00392157 | 0.00000003 | **2** / 262144 |
| 90° | 0.00392157 | 0.00000001 | **1** / 262144 |
| 180° | 0.00392157 | 0.00000004 | **3** / 262144 |

最大差 **恰好 = 1/255**（一个 8bit 量化步），差异分量占 **0.0004%~0.001%** ⇒ **就是同一张图**。

原因很简单：这块网格体是平整的、UV 又恰好是 0–1 的正投影，于是
`UV = (x/W, y/H)` 与 `Generated` **数值上就是同一个东西**。
⇒ **"坐标源接的是哪个插座"这件事，渲染读数、影像比对、肉眼观察，全都看不出来。**

**唯一能证伪的做法 = 扰动 UV 再看图案跟不跟。** 因为 `Generated` 是"按包围盒归一化的局部坐标"，
**完全不看 UV** —— UV 怎么改它都纹丝不动。所以把 UV 每个点的 `(u,v)` 互换：如果条纹真的由 UV 驱动，
它在 0°（此时 `t ≡ u`）下应该**从竖条变成横条**。实测（192×192 / 8 采样）：

```
orig   192x192 gradX=0.02615 gradY=0.00292  比值=  8.969     ← 原始 UV，竖条
swap   192x192 gradX=0.00277 gradY=0.02615  比值=  0.106     ← ★ 互换 u/v，变横条
back   192x192 gradX=0.02615 gradY=0.00292  比值=  8.969     ← 逐点还原后回到 8.969
```

- 朝向翻转 **85 倍**（8.969 → 0.106）⇒ **不可能是噪声蒙的**，图案确实由 UV 驱动；
- UV 逐点还原的**最大偏差 = 0.0**（断言必须恰好为 0，不是"小于容差"）；
- 还原后比值与原始**偏差 0.00%** ⇒ 还原干净、没有留下半改造状态。

脚本：`verify_uv_source.py`（读改前值 → 写入互换 → 渲染 → 断言写入生效 → 逐点还原 → 断言
**逐位相同** → 再渲染确认读数回到原样 → 兜底再还原一次）。

## 4. 核验：可证伪的读数

两个脚本分工：`verify_sweep_angle.py` 管**方向与归一化**，`verify_uv_source.py` 管
**坐标源到底是不是 UV**（这两件事没有交集，合成一个脚本只会让判据变糊）。

### 4.1 `verify_sweep_angle.py` —— 三层

1. **结构断言**（23 条连线逐条比对 + 旧的一维连线已断开 + **坐标源 = `坐标_纹理.UV`**
   + **`Generated` 已断开** + 目标网格体有 UV 层 + `数学_倍频` 入线数 = 2 + 取模运算类型 + 混合类型与系数）
2. **驱动行为**（不是看 `is_valid`，是**改值看跟不跟**）：
   - 角度 0/30/45/90/135/180/270/360° ⇒ 余弦/正弦与 `cos(radians θ)/(|cos|+|sin|)` 逐点吻合，且 `cos²+sin² = 1`
   - `扫过条数` 1.0 / 2.5 / 4.0 ⇒ 条数节点同步
   - `扫过速度` 0.5 / 2.0 + 帧号 +1 ⇒ 相位每帧步进 = 速度/fps
3. **渲染实测**（临时正交相机俯视，256×256 / 16 采样，渲完还原相机与渲染设置）：
   - 四个角度各渲一张，算 `gradX/gradY`（上表）
   - ★ **归一化的可证伪判据**：把 `t = (u·cosθ + v·sinθ)/(|cos|+|sin|)` 按 1.0 取模后分 128 箱，
     数「沿 t 方向的条数」—— 四个角度**必须完全相同**。实测 **`[4, 4, 4, 4]`**；
     若不除那个分母，45° 会多出 √2 倍 ⇒ 条数写成 5 或 6，一眼看得出来。
   - ★ **180° 是 0° 的逐像素左右镜像**：全图平均差 **镜像 0.001884** vs **同向 0.273658**（小 **145 倍**）；
     同时量 0° 图**自身**的左右不对称度 = **0.273729**（与同向差同量级）
     ⇒ 这个判据**不会自动成立**（图案本身强不对称），"反向"是逐像素成立的。

### 4.2 `verify_uv_source.py` —— ★★ 坐标源的决定性判据

结构断言只能证明"线接在 `UV` 插座上"；对这个平整网格体，`UV` 与 `Generated` 的**渲染逐像素相同**
（§3.12），所以渲染也证不了。**唯一能证伪的做法是扰动 UV**：

1. 结构：`分离_XY.Vector` 恰好 1 条入线且来自 `坐标_纹理.UV`、`Generated` 已断开、目标有 UV 层；
2. 读原始 UV → 渲 0°（此时 `t ≡ u`，应**竖条**）；
3. **临时把每个点的 `(u,v)` 互换** → 断言写入生效 → 渲 0°（应**横条**）；
4. **逐点还原** → 断言**最大偏差恰好 = 0**（不是"小于容差"）→ 再渲 0°（读数应回到原样）。

一整套跑完的读数：

| 阶段 | `gradX/gradY` | 结论 |
|---|---|---|
| 原始 UV | **8.969** | 竖条（沿 U） |
| ★ UV 互换 | **0.106** | 横条 ⇒ **图案确实由 UV 驱动**（`Generated` 不看 UV，改不动） |
| 还原后 | **8.969** | 偏差 0.00% ⇒ 还原干净 |

朝向翻转 **85 倍**（8.969 → 0.106），不可能是噪声蒙的。脚本还把 UV 坐标的还原写成
**断言 `最大偏差 == 0.0`**，并在 `finally` 里兜底再还原一次 —— 宁可多还原一次，也不留半改造状态。

## 5. 文件

| 文件 | 作用 |
|---|---|
| `probe_sweep.py` | **只读**侦察：目标对象 / 材质 / 21 个节点 / 连线 / 驱动 / 旋钮 / 平面世界包围盒与法线轴 |
| `build_sweep_angle.py` | **幂等**构建：空对象 + 旋钮 + 21 节点 + 23 连线 + 6 驱动；含**色标指纹安全闸**与 **UV 层守卫**（见下）；顶部 `COORD_SOURCE` 选 `UV` / `Generated` |
| `verify_sweep_angle.py` | **独立核验**：坐标源结构 + 驱动行为 + 四角度渲染 + 自包含预览 HTML（同目录有 `baseline_generated_<角度>.png` 时会并列显示"改前"） |
| `verify_uv_source.py` | ★★ **坐标源决定性核验**：临时互换 UV 的 `(u,v)` 看朝向翻不翻；逐点还原并断言偏差为 0 |
| `maintain_ctrl.py` | **非破坏**维护：只对齐驱动器与旋钮，**绝不碰节点/连线/色标**；跑完"0 处改动" = 健康 |

> ⚠️ `build_sweep_angle.py` 的**安全闸**：它默认会清空并重建整棵节点树，而**色标是你的手调成果**。
> 脚本开跑前先比对两个 ColorRamp 的指纹，只要不是出厂的 3 档黑/白/黑（且**本次真的要重建**）就**拒绝执行**并列出被改的色标；
> 确认要重建才把顶部 `FORCE_REBUILD` 改成 `True`。改完色标后想"只修驱动"，跑 `maintain_ctrl.py`，**别跑 build**。
> ★ 闸的门槛是「**本次是否真的会重建**」而不是「色标是否被改过」：结构已经正确 ⇒ 走跳过分支 ⇒ 根本没有重建
> ⇒ 不该拦（否则幂等复跑会被误伤）。此时它会打一行 `色标已被手工改过…但结构已正确、本次不重建,色标原样保留` 然后 `BUILD_OK`。
> 三个脚本送桥跑；桥 `exec` 环境里 **`__file__` 不存在**，所以脚本内**所有路径写绝对常量**。
> 送桥的脚本**不能带 BOM**（PowerShell 5.1 的 `Out-File -Encoding UTF8` 会写 BOM ⇒ 桥端 `SyntaxError: U+FEFF`）。

### 撤回

材质挂在 `平面` 的 0 号槽上（原槽材质会 `use_fake_user=True` 留着）。要撤回：

```python
ob.material_slots[0].material = D.materials["原材质名"]   # 或在 GUI 里改回
```

删除 `渐变控制` 空对象即可废掉全部驱动器（材质保留，但参数不再有源）。
本主题的所有改动都只发生在**内存**里 —— 桥不存盘，**要按 Ctrl+S 才会落下**。

## 6. 未做（如需要请另行确认）

- **没有做常驻 N 侧栏面板**：用户明确"不需要"。参数就在**物体属性 → 自定义属性**里
  （或 3D 视图按 N → 条目 → 最底部）。`Text.use_register` 在 5.2 也不存在，做不成"重开自动跑"。
- **没有把扫过链打包成节点组**：现在参数是"5 个空对象属性 + 6 条驱动器"。
  打包成 `节点组` 后可以只暴露 4 个输入口，但那样驱动器就得挂到组外/组内两处，反而更难改色标 ——
  本主题的取舍是**保留平铺、看得见摸得着**。
- **坐标源已经是真实 UV**（`坐标_纹理.UV`，见 §2.8）。想退回包围盒归一化就改
  `build_sweep_angle.py` 顶部的 `COORD_SOURCE = "Generated"`（或手工换那一根线）。
  注意 **UV 版要求网格体有 UV 层**，所以材质搬到别的网格体之前先确认对方有 UV。
- **没有做"UV 层选择"**：`坐标_纹理.UV` 用的是**渲染活动 UV 层**，不做按名字指定。
  要按名字指定得换成 `ShaderNodeUVMap` 节点 + `uv_map` 属性；但那样材质搬到没有同名 UV 层的
  网格体上会**静默返回全 0**（图案塌成一种颜色），可移植性反而更差 —— 本主题刻意不用它。
- **`扫过角度` 没有做"多圈"语义**：超 360° 只是同一方向，不做累计旋转。
