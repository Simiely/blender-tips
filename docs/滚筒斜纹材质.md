## 1. 原理

### 1.1 柱面坐标 → 斜纹

```
u = (atan2(y, x) + π) / 2π          绕柱角度归一化（y 是分子、x 是分母）
v = z / 柱高                        高度归一化
f = u×K − (v + 上升偏移)×N          螺旋合成
p = FLOORED_MODULO(f, 1)            周期相位
```

- **锚点空物体放"柱底面中心"**、rotation 全 0 / scale 全 1
  ⇒ `Object` 坐标的 `z` 天然落在 `[0, 柱高]`，`v` 归一化**少一个减法节点**
  （放几何中心也行，但 v 要多一次 `−zmin`；放原点则是错的，`atan2` 的极轴会离开柱轴）
- **`SUBTRACT`（`u×K − v×N`）决定条纹是 `/` 形**（左下→右上）；改成 `ADD` 就是 `\` 形
- **必须 `FLOORED_MODULO`**：偏移为负时 `f` 取负，普通 `MODULO` 的语义会把条纹底部裁掉

### 1.2 波形走 Math 域（不让 ColorRamp 兼职）

```
前缘 = MapRange(SMOOTHSTEP,  0 .. A  →  0 .. 1)      A = 前缘宽度
拖尾 = MapRange(SMOOTHSTEP,  B .. 1  →  1 .. 0)      B = 拖尾起点
mask = MINIMUM(前缘, 拖尾)                            ⇒ 快升 / 平台 / 慢降
```

**为什么不用 ColorRamp 的色标位置去编码曲线**（旧做法的三条死结）：

| 症状 | 根因 |
|---|---|
| 用户抱怨"色标拖不动" | 中间 4 个色标被驱动锁死 |
| 改一个滑块会同时改亮峰位置 / 前缘 / 后缘 | 三个参数挤进一个耦合公式 |
| 拖尾长度上不去（w=0.4 时最多 58%） | 拖尾空间 = `1 − (亮峰 + 半宽)`，结构性受限 |

**根因一句话**：用「颜色节点的色标位置」去编码一条数学曲线，是把几何信息塞进了颜色容器。
拆开后：参数正交、都挂在 **socket** 上（驱动路径就是 `inputs[N]`，比色标路径稳得多）、
**ColorRamp 零驱动**（用户可自由加色标）、拖尾能开到 99%。

- `p=0` 与 `p=1` 处 mask 都是 0 ⇒ **首尾同值，绕一圈无缝**
- `A = 1 − B` 时退化成对称条纹（所以"对称"是特例，不是另一套代码）

依据（Blender 官方手册）：`Map Range` 支持 `Smooth Step` / `Smoother Step` 插值；
`Math → Wrap` 用于"repeat automatically as the input increases"。

## 2. 两套并列方案

**两种调参入口的语义互相打架**，塞进同一套控件一定有一个是"死"的：

| 入口 | 斜角 | 问题 |
|---|---|---|
| **按条数** | 由 `K:N` 算出（结果） | 想指定角度就得凑比值，只能取到离散几档 |
| **按角度** | 直接给（`N` 反算） | **K 固定时改斜角会连带改可见条纹数** |

⇒ 做成两份并列，**跑哪个装哪个**：

| | **A · 按条数** | **B · 按角度** |
|---|---|---|
| 材质 | `滚动效果网格体_滚筒斜纹_按条数` | `滚动效果网格体_滚筒斜纹_按角度` |
| 槽位 | 0 | 0（跑哪个装哪个） |
| 控件 | K + **高度周期数 N** | K + **斜角** |
| 节点 / 连线 | 18 / 20 | 22 / 25 |
| 建脚本 | `build_streak_count.py` | `build_streak_angle.py` |

**B 的斜角反算链**（节点内实时算，所以改 K 时斜角自动保持）：

```
斜角(度) ─RADIANS→ 弧度 ─TANGENT→ tanθ ─┐
条纹数量K ─× (柱高/周长) ───────────────÷──→ N ─→ 高度条纹N
```

**为什么不要长期并存**：两者共用同一个锚点空物体（纹理坐标必须指向同一个），
并存会让控制空物体上留下**对方用不到的"幽灵参数"**（典型：「斜角」在按条数方案里没有任何节点引用）。
所以两边都带一个 `cleanup_variant_X()`，装自己时清掉对方；另一方的建脚本始终保留，随时可重装。

## 3. 参数

| 控件 | 默认 | 范围 | 说明 |
|---|---|---|---|
| 条纹数量 K | 3 | 1 ~ 24 | 绕柱一周的条数。**必须整数**（绕柱方向是闭环） |
| 高度条纹数 N（方案 A） | 2 | 1 ~ 24 | 沿柱高的周期数。不必整数（柱高方向不闭合） |
| 斜角（方案 B） | 41° | 5 ~ 85 | 高度周期数由它与 K 反算 |
| 前缘宽度 A | 0.12 | 0.005 ~ 1 | 升到最亮占周期的比例。越小头越尖 |
| 拖尾起点 B | 0.22 | 0.005 ~ 1 | **拖尾长度 = 1 − B**（默认 0.78） |
| 上升速度 | 0.01 | −0.2 ~ 0.2 | 每帧沿柱高流动多少。**正 = 右下→左上** |
| 旋转速度 | 0 | −0.2 ~ 0.2 | 额外绕 Z 轴转（默认 0 = 纯上升） |
| 发光强度 | 5 | 0 ~ 100 | 亮度倍数 |

**形状配方**：对称条纹 `A=0.35 B=0.65` · 流星（默认）`0.12 / 0.22` · 细长流星 `0.04 / 0.14` · 硬边 `0.5 / 0.5`

## 4. 实测数据

### 4.1 运动方向 —— 纸面推导推反了，以实测为准

我先在纸面上推了一套"等值线平移"的公式，得出 `up = −frame×速度` 才对，
**实现后实测是往右下走的**。改用固定高度一行的暗带中心跨帧比对：

| 驱动表达式 | 两帧间暗带位移 | 结论 |
|---|---|---|
| `−fr * us` | `+0.29 / +0.32`（右移） | ✗ |
| `+fr * us` | `−0.32 / −0.29 / −0.28 / −0.19 / −0.21 / −0.31`（左移） | ✔ |

**⇒ 这类符号问题不要推理，要测量。** 想让条纹往右上走，把「上升速度」取负。

### 4.2 斜角 ↔ 高度周期数（方案 B，固定 K=3）

| 斜角 | N | 观感 |
|---|---|---|
| 20° | 4.75 | 密集、接近水平 |
| 30° | 2.99 | K:N = 1:1 |
| **41°** | **1.99** | 默认 |
| 60° | 1.00 | 偏竖直 |
| 75° | 0.46 | 接近竖直、不足一个周期 |

### 4.3 端到端波形验证

隔离临时场景、正交正视、Standard 线性输出，把屏幕像素重采样到**柱面角度 φ 空间**，
与**独立重算**的理论 mask 逐点对比：

```
φ      -1.250  -1.042  -0.833  -0.625  -0.417  -0.208   0.000   0.208   0.417   0.625   0.833   1.042   1.250
实测   0.5199  0.2694  0.0750  0.0025  1.0000  0.9904  0.8624  0.6428  0.3926  0.1614  0.0196  0.6347  0.9966
理论   0.5111  0.2647  0.0746  0.0009  1.0000  0.9894  0.8648  0.6468  0.3944  0.1666  0.0224  0.5393  1.0000
```

## 5. 坑（都用实测定过）

### 5.1 端盖必须单独分槽，否则条纹摊成"扇形风车"

端盖面上的 `atan2(y,x)` 是**极角**。竖条纹的 `f = u×K` 映射到端盖上，
`u ∈ [0,1)` 绕中心一圈 ⇒ 亮区在端盖上就是 K 个**扇形扇叶**（俯视像风车）。

**正解**：按**法线**把端盖面分到独立材质槽（纯黑）：

```python
p.material_index = CAP_SLOT if abs(abs(p.normal.z) - 1.0) < 1e-3 else SLOT_INDEX
```

⚠️ 判定必须用**法线**，不能写死面索引（换模型索引就变）。
⚠️ 端盖通常看不见，但俯视 / 斜视 / 用户转视角时一定露馅 —— 别省这一步。

### 5.2 隔离临时场景渲染时，节点树驱动不被求值

**现象**：`evaluated_get(dg).node_tree` 读到的驱动值**全对**，
但渲染出来是**建材质时的旧 default**（K=1 / spin=0 / 强度=1.0）。
改 `default_value`、link 控制空物体进临时场景、切活动场景、`depsgraph.update()` —— **全都没用**。

**症状极具迷惑性**：数值核验全绿，只有渲染不对，极易误判成"材质坏了"。

**处置**（按可靠性）：
1. **改 ctrl 的值**（让值真的变化）+ `touch()` ⇒ 生效
2. 要渲染**固定**参数时：**把驱动整个移除**（`node_tree.animation_data_clear()`），
   手动把值烘进 `default_value`，渲染完再 `exec` 建脚本恢复
3. 别指望 `update_tag()` / `view_layer.update()` / `depsgraph.update()` 能解决

### 5.2b 端盖材质会「丢」—— 症状：柱子上出现扇形 + "有一节对不上"

实测遇到：`material_slots` **只剩 1 个槽**，**全部 34 个面（含 2 个端盖）都指向条纹材质**。
端盖于是用柱面坐标投影 ⇒ 条纹摊成 K 个**扇形**（俯视像风车），看起来就是"有一节对不上"。

**触发**：任何一次 `materials.clear()` / `pop()` / 手工增删槽位，都会让"端盖黑"那个槽消失，
而面索引仍指向条纹槽 ⇒ **端盖静默变条纹**。

**正解**：建脚本每次重建端盖材质并重新分配；核验要断言「两个端盖面都指向端盖槽」，
且**按材质名定位、不写死槽位索引**。

### 5.2c 整数类参数必须在【驱动里取整】

用户拖滑块会拖出小数（实测 `高度条纹数 = 2.5399999618530273`）。
K 非整数 ⇒ 绕柱接缝错位半格；N 非整数 ⇒ 柱顶/柱底条纹错开。
`IDProperty` 的 `step=1` **挡不住**（只影响拖拽手感）。

**正解**：驱动表达式取整 —— `floor(x + 0.5)` / `round(x)` / `int(x + 0.5)` 在 Blender 5.2 里都可用：

```python
bind_drive(nt.driver_add(p, -1), 'floor(kn + 0.5)', {'kn': V['kn']})
```

### 5.5 ★ 贴到「别的对象」上后看不出动态——两个真原因（实测）

**① 尺度不匹配：对象比条纹周期小几百倍 ⇒ 整块落在同一个条纹里**

材质把**世界空间坐标**当柱面坐标，前提是"对象就是那根柱子"。实测把材质贴到 scale ≈ 0.01~0.02
的小球上（而条纹周期是世界尺度 ≈ 7.9 单位），**整个球落在一个条纹内** ⇒ 渲染出来是**纯色**
（实测图内亮度 min=max），既看不到条纹也看不到动。

**修复**：复制一份材质，把 `纹理坐标.Object` **清空** ——
`Object` 输出就变成对象的**局部坐标**，条纹尺度自动适配每个对象，每块网格各自成为"一根小柱子"：

```python
dst = src.copy(); dst.name = src.name + '_自适应'
next(n for n in dst.node_tree.nodes if n.type == 'TEX_COORD').object = None
```

> 驱动仍共享同一个锚点空物体 ⇒ 速度/形状/强度依然统一可调。

**② 相位步长恰好是整数 ⇒ 两帧同相，看着像静止**

实测参数 `上升速度 = 0.2`、`N = 3` ⇒ 每帧相位跳 **0.6 个周期**
⇒ 1.7 帧就走完一个条纹周期（24fps 下等于频闪）；
更巧的是 `Δframe × 速度 × N` 在某些帧差下正好是 **整数** ⇒ 那两帧**逐像素完全相同**（实测差 0.00000）。

**修复**：把每帧相位控制在小步长，经验值 **0.01 ~ 0.05 周期/帧**：

| 上升速度 × N | 相位/帧 | 一个周期 | 观感 |
|---|---|---|---|
| 0.2 × 3 | 0.60 | 1.7 帧 | 频闪，且整数帧差时完全同相 |
| **0.01 × 3** | **0.03** | **33 帧** | **流畅** |

### 5.6 ★ 判断「到底有没有动态」别只看渲染——直接读驱动真值

隔离临时场景里节点树驱动**不会自动求值**（见 §5.2），所以"渲染两帧对比"这个方法
在隔离场景下**不可靠**（实测连正常在动的柱子也测出 0 差异）。
**可靠的判据是直接读求值依赖图里的驱动真值**：

```python
def phase(f):
    bpy.context.scene.frame_set(f); bpy.context.view_layer.update()
    dg = bpy.context.evaluated_depsgraph_get()
    ev = mat.evaluated_get(dg).node_tree
    up = ev.nodes['上升偏移'].inputs[1].default_value
    n = ev.nodes['高度条纹N'].inputs[1].default_value
    return (up * n) % 1.0
# 逐帧看相位是否都在推进、且步长不是整数
```

实测（修好参数后）：`365→375` 每帧相位 `+0.0300`，连续推进 ✓

### 5.4 旧版 `滚动效果网格体_竖条旋转` 的「斜角」驱动失效

实测该材质 7 条驱动里有 1 条失效：
`nodes["斜角_弧度"].inputs[0] ← ang`，变量指向 `ctrl["斜角"]` —— 而 `斜角` 这个属性
后来被新版清理掉了（按条数方案不用它）。

```
✗ nodes["斜角_弧度"].inputs[0].default_value = ang
   变量 ang → OBJECT '竖条旋转控制'["斜角"]
   ★ 属性 '斜角' 在对象上【不存在】！现有键: [条纹数量, 旋转速度, 发光强度,
     前缘宽度, 拖尾起点, 上升速度, 高度条纹数]
```

- **表现**：高度周期数退回默认值（条纹疏密不对），但**上升动态还在**（`fr * us` 仍有效）
- **修复**（不必重建材质，补回属性即可）：

```python
bpy.data.objects['竖条旋转控制']['斜角'] = 41.0
```

> ⚠️ 反过来说：**两份材质共用同一个锚点空物体**，所以清理控件属性时要先确认
> 旧的材质是不是还在用那个键 —— 否则会静默留下失效驱动。

### 5.3 其它已记录的坑

- **`bpy.data.images` 按【文件路径】缓存** —— 渲染覆盖同名 PNG 后再 `load()`，
  拿回的是第一次的旧像素（症状：多次运行"连字节数都一样"）。用唯一文件名 + `reload()`
- **`Image.pixels` 对 PNG 返回 sRGB 编码值**（证据：强度 0.6 时读数上限 = 0.7974 = sRGB(0.6)）
- **`ortho_scale` 对应的是【较长边】**：420×900 + `ortho_scale=15.5` ⇒ 水平比例是 `900/15.5 = 58.06 px/单位`，
  不是 `420/15.5 = 27.10`。用错会让水平比例差一倍，把 1.59 个周期误判成 1 个
- **比"渲染像素 vs 理论曲线"前必须先自证 φ 空间映射**（量柱子在画面里的像素跨度 / 查垂直起伏 / 数亮带条数）。
  对齐后相关系数从 0.07 跳到 0.9989 —— 差别全在映射，不在材质
- **斜角越大，屏幕上条纹越弯、间距越不均** —— 柱面投影固有（`x = R·sinφ` 非线性），不是缺陷

## 6. 复用清单（换工程时）

1. **先跑 `recon_cylinder.py`**：逐顶点求世界包围盒 → 确认半径恒定 / 轴向 / zmin / zmax，
   并核对锚点偏差（应全为 0）
2. 改建脚本顶部配置区（`AXIS_X/Y`、`Z_BOTTOM`、`HEIGHT`、`CYL_RADIUS`）
3. 跑建脚本 → 跑 `verify_variants.py`（**另开一次请求**）
4. 渲染多帧 + 测位移方向（`shift_check` 那套方法）确认方向符合预期
5. 满意后提醒用户 **Ctrl+S**（桥只改内存）
