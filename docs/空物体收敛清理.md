# 空物体收敛清理（EMPTY 不动点算法）

**场景**：第三方模型（3ds Max / 3d66 等）导入的工程，Outliner 里躺着几千个空物体层级容器 ——
`Untitled.001~999+`（Max 哑物体）、`Group-*`、`Line*` / `Arc*`、`VRayProxy`、`穹顶灯`、`PhysCamera*` 之类。
它们不渲染、不参与任何动画，只让 Outliner、选择、视图层操作变卡。

**目标**：把「不支撑任何几何的空物体」清干净，且**一根线都不动**（可见几何逐位不变）。

**配套**：[`scripts/scene-cleanup/`](../scripts/scene-cleanup/)（脚本包）·
[`skills/blender-scene-cleanup/`](../skills/blender-scene-cleanup/)（AI 作业规范）·
传输层见 [技巧速查 §1](技巧速查.md)

---

## 1. 为什么不能"只删无子级的"

真实工程第一次按字面删掉 **5006 个**「无子级」EMPTY 之后，Outliner 里**又长出 2026 个无子级 EMPTY** ——
原本挂着那些叶子的中转容器（`Group-*` / `Arc*` / `Line*`）自己变成了叶子。

所以这不是一次性过滤，而是**求不动点**：删 → 重新算 → 再删 … 直到没有可删的。

> ⚠️ 每轮都全量重扫会撞桥的 **120s 上限**（客户端超时后结果即丢，而脚本仍在主线程跑、后续请求只排队）。
> 必须**一次算准最终可删集**。

## 2. 判定算法：引用图 + 不动点

```
一个 EMPTY 需要保留  ⟺  它「支撑」某个非 EMPTY 对象
「支撑」= 以下任一（传递闭包）：
  a) 直接挂着一个非 EMPTY 子级（MESH / CAMERA / LIGHT / CURVE …）
  b) 子级里有一个"需要保留"的 EMPTY
  c) 被一个"需要保留"的对象引用（约束 target / 修改器指针 / 驱动变量）
  d) 被外部数据块引用（材质节点 OBJECT socket / 场景相机 / 相机 DOF 焦点 / 粒子 dupli_object …）

不满足以上任一条的 EMPTY  →  全部可删
```

实现三步：

1. **继承图**：自己建 `parent.name -> [child, ...]` 映射（**不要**在循环里用 `ob.children`，那是对全场景的 O(n) 重算，17k 对象量级会卡死）
2. **引用图**：种子 = 所有非 EMPTY 对象 + 所有被外部数据块引用的对象
3. **不动点迭代**：每轮把满足 a/b/c 的 EMPTY 加进保留集，直到一轮无新增（实测 2~3 轮收敛）

判定"引用"时**必须排除**这几项，否则全场景对象都会被误标成"被引用"：

| 属性 | 为什么不是引用 |
|---|---|
| `Scene.objects` / `Collection.objects` / `ViewLayer.objects` | **成员关系**，不是逻辑引用 |
| `Collection.all_objects` | 递归成员关系 |
| `ID.original` | 副本来源指针 |

## 3. 三重安全闸

| 闸 | 内容 |
|---|---|
| 1 | 只删 `ob.type == 'EMPTY'`，其它类型一律跳过 |
| 2 | 靠不动点规则保证：删完**不会有非 EMPTY 对象失去父级** |
| 3 | 靠引用图保证：删完**不会有保留对象产生悬空引用** |

**为什么删了不影响画面**（可直接向人论证）：

* 删除的永远是"叶子链"，父→子是单向的，删子不影响父 ⇒ **不可能改变任何物体的世界变换**
* 留下的 EMPTY 里，凡「直接挂着非 EMPTY 子级」的那个计数**必须完全相等**
* 「非 EMPTY 对象数」在删前删后**必须完全相等** —— 最强的一条断言，写进核验脚本

## 4. 作业流程（三步，必须分三次请求）

| # | 脚本 | 作用 |
|---|---|---|
| 1 | `snapshot_baseline.py` | 清理前基线 → `cleanup_baseline.json` |
| 2 | `purge_empties.py` | 跑不动点、落名单、执行删除、自检 |
| 3 | `verify_purge.py` | **另起一次请求**的独立核验，读磁盘基线做前后对比 |

> ⚠️ **修改与验证必须分两次请求**：同一次 `exec` 内改完立即读会读到未刷新的缓存值。

**建还原点**（在跑第 2 步之前）：

```powershell
Copy-Item "<工程>.blend" "<工程目录>\_backup\<名>.before-emptypurge.blend" -Force
# 比对字节数一致再往下走
```

桥只改内存不存盘 ⇒ 跑完要提醒用户 **Ctrl+S**；不满意 `File > Revert` 即可回到清理前。

## 5. 独立核验清单

另起脚本（不复用执行脚本的内存状态），逐条过：

1. **名单残留 = 0** —— 被删的名字不该还能 `bpy.data.objects[...]` 到
2. **非 EMPTY 对象数、MESH / CAMERA / LIGHT 数、材质 / 集合 / 场景数 全等**
3. **父级丢失 = 0**
4. **悬空约束 = 0**（TRACK_TO / COPY_\* / DAMPED_TRACK / IK / FOLLOW_PATH / CHILD_OF / SHRINKWRAP … 的 `target` 不该是 None）
5. **可见几何包围盒逐位一致** —— 所有非 EMPTY 对象的 `matrix_world @ bound_box` 的 min/max 前后相同（"没动几何"最硬的证据）
6. **EMPTY 无子级 = 0**（收敛标志）
7. **真缺失贴图 / 链接库 / 字体 / 声音 = 0**
8. **孤儿数据块 = 0**（若本轮目标是清孤儿）
9. 输出**最终保留的 EMPTY** 的集合 / 命名族分布，让人能核对留下来的都是合理中转节点

## 6. 实测（真实工程 `260910xAx01`，22315 对象 / 5867 网格）

| 项目 | 最初 | 删一轮后 | 收敛后 |
|---|---|---|---|
| 总对象 | 22315 | 17309 | **14848** |
| EMPTY | 11775 | 6769 | **4308** |
| **EMPTY 无子级** | 5006 | 2026 | **0 ← 收敛** |
| 非 EMPTY 对象 | 10540 | 10540 | **10540** |
| MESH / CAMERA | 10527 / 13 | 10527 / 13 | **10527 / 13** |
| 材质 / 集合 | 236 / 10 | 236 / 10 | 236 / 9（另清了一个空集合） |

* 两轮累计删 **7467** 个 EMPTY（5006 + 2461 级联）
* 删除耗时 **71.88 s**（14848 对象规模），引用图扫描 **12~20 s**
* 可见几何包围盒 **逐位一致**：`min(-1348.71, -428.05, -958.45)` / `max(1348.71, 428.05, 439.90)`
* 留下来的 4308 个 EMPTY 里，**3064 个直接挂着网格/相机**，其余是支撑这些链条的中转节点

被删构成：`Untitled.*` 3401 个（无名 Max 哑物体）、`3d66-*` 34 个（粒子流算子残留）、`Group-*` 838 个、
`Line*` / `Circle*` / `Arc*`，以及 `VRayProxy` / `穹顶灯` / `vraysunlight` / `PhysCamera*` 等专业辅助体。

## 7. 坑（都踩过）

1. **`bpy.data.objects.remove()` 后旧引用立即失效** —— 连 `o.name` 都会抛
   `ReferenceError: StructRNA of type Object has been removed`。
   ⇒ **所有要用的字段必须在删除前冻结成纯 Python 值**（str/int/tuple），核验一律重新 `list(bpy.data.objects)`。
   同一个坑连踩两次才写进文档。
2. **不要用 `bl_rna.properties` 全属性遍历上万对象** —— 22315 个对象全属性遍历约 **7 分钟**，必超 120s。
   改用**打靶式**：约束 `c.target` / 修改器指针 / 节点 OBJECT socket / 驱动 `variable.targets[*].id` /
   `Scene.camera` / 相机 `dof.focus_object` / 粒子 `dupli_object|instance_object`。全场景 **12~20s**。
3. **`Scene.objects` / `ID.original` 不是引用** —— 见 §2 表，否则 5006 个对象全被标成"被引用"。
4. **不要在循环里用 `ob.children` / `ob.all_objects`** —— 每个都是 O(n) 重算。
5. **空集合 ≠ 空对象** —— `Export` 这类集合 `objects=0` 但 `users=1`（挂在场景根），
   删法 `bpy.data.collections.remove(col, do_unlink=True)`，**要单独问用户**别顺手删。
6. **判"贴图缺失"必须带 `not img.packed_file`** —— 否则会把"路径失效但已打包"的贴图误报为缺失（真实工程有 105 个这种）。
7. **`users == 0` 的数据块存盘时根本不写进 `.blend`** —— 所以"显式删除"与"存盘丢弃"结果等价；
   但**只打包在 .blend 里、磁盘无副本**的数据块一旦变孤儿，存盘即**永久丢失** ⇒ 删孤儿前必须先判磁盘有没有同名副本。
8. **桥 120s 超时后脚本仍在跑**，期间桥对外无响应、新请求只排队 ⇒ 长任务要**状态逐阶段写盘**，超时后读盘回捞。
9. **经桥执行的脚本禁止 `if __name__ == "__main__"`** —— 桥的 `_env()` 命名空间里没有 `__name__`，直接 `NameError`；结尾无条件 `main()`。

## 8. 顺带能一起收掉的（同一轮排查）

| 项 | 判定 | 处理 |
|---|---|---|
| 孤儿材质 | `users == 0` | 先材质**再**图像（删材质会带出新孤儿图像） |
| 孤儿图像 | `users == 0` | 删前判**磁盘有同名副本**或已打包 |
| 空集合 | `objects=0` 且 `children=0` | `bpy.data.collections.remove(col, do_unlink=True)`，单独问用户 |
| 缺失贴图 | `source=='FILE'` 且 `filepath` 非空 且 `not packed_file` 且 `os.path.exists(abspath)` 为假 | 见 [3dsmax导入场景清理与轴心修复.md](3dsmax导入场景清理与轴心修复.md) |
| 空 action slot | 随空物体删完留下的空槽 | 存盘时 Blender 自己丢掉，不用管 |

真实工程收尾一轮：5 个孤儿图像（`3d66Model-*` 两张 + 3 张补回的 `_2115_*` 法线）+ 1 个空集合 `Export`，
清完 `images 114 → 109`、`collections 10 → 9`，**对象 / 网格 / 相机 / 材质全部不变**。
