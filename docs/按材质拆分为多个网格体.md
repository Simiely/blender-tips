# 按材质拆分为多个网格体

> 来源: `E:\desktop\260910\游里屋顶街区模型(水晶版)\260910xAx01.blend` 实战
> (对象 `对象13735`:3,505,328 面 / 2,020,266 顶点 / 4 个材质槽)
> 适用: Blender 5.2 LTS
> 脚本包: [`scripts/separate-by-material/`](../scripts/separate-by-material/)

## 场景

一个对象挂了**多个材质槽**,几何上本来就是分开的几块(比如:结构件 + 灯罩 + 玻璃 + 自发光条)。
想拆成独立对象,便于**单独隐藏 / 换材质 / 导出 / 做 LOD**。

难点不在"能不能拆",而在:

1. 拆完**世界位姿必须一模一样**(不能有位移漂移);
2. 拆完**几何不能丢、不能多**;
3. 属性层(UV / 自定义拆分法线 / 锐边)不能坏;
4. 拆完得知道**有没有下游系统引用过原对象**(它现在只剩一部分几何了)。

## 权威依据(先查再做)

### 1. 官方手册原文(Blender 5.2 LTS)

`modeling/meshes/editing/mesh/separate.html`,By Material 模式:

> *"Splits the mesh into an object per **material slot** … **This is done for the whole mesh
> regardless of the selection.**"*

两条关键信息:**按材质槽**(不是按材质)**、对整网格生效、与选择无关**。

### 2. 运行时 API 自省

```python
bpy.ops.mesh.separate.get_rna_type()   # type 的枚举只有 SELECTED / MATERIAL / LOOSE
```

⚠️ **`bpy.ops.mesh.separate_by_material` 不存在**。但注意这个陷阱:

| 判据 | 结果 |
|---|---|
| `hasattr(bpy.ops.mesh, "separate_by_material")` | **`True`(假阳性!)** |
| `bpy.ops.mesh.separate_by_material.get_rna_type()` | `KeyError` —— 根本不存在 |

> **判 `bpy.ops` 算子存在性,必须用 `get_rna_type()` 包 `try`,不能信 `hasattr`。**

## 机制细节

* **原对象保留哪一组几何 —— 规则不是「最后一个材质槽」**（v1.15.2 修正，旧版本文档表述有误）：
  * **实测 + 源码双向确认的正确规则：面序中「首次出现位置最晚」的那个材质组留在原对象。**
    等价说法：Blender 内部反复「取当前第一个面的材质 → 把该组切走」，**最后剩下的那一组**留在原对象。
  * **源码依据**（`source/blender/editors/mesh/editmesh_tools.cc` · `mesh_separate_material`）：
    每轮取 `BM_iter_at_index(bm_old, BM_FACES_OF_MESH, nullptr, 0)`（当前第一个面）的 `mat_nr`，
    若该材质**已覆盖全部剩余面**（`tot == bm_old->totface`）则
    `mesh_separate_material_assign_mat_nr(bmain, base_old->object, mat_nr)` 并 `break`；
    否则 `mesh_separate_tagged(...)` 把这组面切成新对象、并从原网格移除。
    ⇒ 「最后剩下的那组」正是**首现位置最晚**的那组。
  * **判别实验**（7 个互相排斥的用例 × 4 种候选理论）：只有「首现最晚」全用例成立；
    「最低索引」「最高索引」「最后一个面的材质」**全部被证伪**。
  * **两个真实对象独立印证（累计 9/9）**：
    `对象9041` 各组首现面 = 槽0:1128 / 槽1:0 / 槽2:660 / 槽3:664 ⇒ 槽0 首现最晚
    ⇒ **原对象拿到槽0**（灯光光.001，84,208 面）—— 与实测一致（不是「最后一个槽」）；
    `对象9287` 槽0 首现 3588 / 槽1 首现 0 ⇒ 同样原对象拿到槽0。
  * 推论：**原对象的名字与它拿到的材质常常对不上**，这是既有行为、不是 bug。
* 其余槽各生成一个新对象,名字按槽顺序为 `原名.001` / `.002` / `.003` …
* **每个新网格只保留自己那一个材质槽**(不是保留全部槽)
* 所有部件都沿用原对象的局部变换与 `matrix_parent_inverse` ⇒ 世界位姿**逐位重合**
* 材质数据块本身不变,只是被更少的对象引用

真实验例(槽序 0→3):

| 对象 | 面数 | 材质 |
|---|---|---|
| `对象13735`(原对象,**保留了「首现最晚」的那组**，本例恰为槽3) | 1,051,492 | 艺术渐变蓝紫高光玻璃钢 塑料 VR材质s.001 |
| `对象13735.001` | 84,208 | 灯光光.002 |
| `对象13735.002` | 2,207,860 | 3d66-VRayMtl-23516850-023sd.001 |
| `对象13735.003` | 161,768 | 01 - Defauwaw…(乱名).001 |

> 原对象名字占着,拿到的却是**「首现最晚」那组**的几何 —— 名字与材质对不上,这是 Blender 的既有行为。
> 想要名字清爽,用脚本包的 `RENAME_BY_MATERIAL = True` 把**新部件**按材质重命名(原对象名不动)。

### 空材质槽（有材质但零面）会怎样

* **不产生对象**：循环只遍历**面的** `mat_nr`，从不遍历材质槽 ⇒ 空槽既不被保留、也不会被切出去。
* **会被自动清除**：`mesh_separate_material_assign_mat_nr` 把数据块 resize 到 **1 个槽**，
  所以拆分后每个部件的材质槽数恒为 1，空槽自然消失 —— **无需事先手工清理**。
* 因此 **部件数 = 「有面的」材质槽数**。若拿材质槽总数当判据，凡有空槽的对象都会被误报为异常
  （v1.15.2 前的验证器正是这个毛病，已修正）。
* 副作用：空槽对应的材质 `users` 会**下降**（它少了一个引用者）。**下降本身不一定是问题，
  归零才是** —— 见下一小节。

#### ⚠️ 空槽材质会被「存盘」丢弃（实测三级分辨）

| 阶段 | 空槽材质状态 |
|---|---|
| 拆分前 | `users=1` |
| **拆分后（未存盘）** | 数据块**仍然存在**，`users=0` |
| 存盘后（同进程） | 仍 `users=0`（Blender 不立即释放） |
| **重新打开文件** | **不存在** —— 落盘时被当作孤儿丢弃 |

结论：**拆分算子不删材质**，是 **Blender 的存盘孤儿清理**删的。
所以若该材质**只被本对象引用**，「拆分 + `Ctrl+S`」就等于**永久丢失**。
（真实场景 `对象9287` 的两个空槽材质另有使用者，`users` 3→2，**不受影响** —— 判定要看是否归零。）

**要保留怎么办**：拆分前给这些材质打 `use_fake_user = True`
（脚本包 `separate_by_material.py` 的 `KEEP_EMPTY_SLOT_MATERIALS = True` 已内建；
实测材质存活、`fake=True`、验证 24 项全绿），或者先手工清空/移走这些槽。

验证器第 9 节据此**分级判定**：`[有面槽]` 材质丢失 = ❌ 真问题；`[空槽]` 材质消失或归零 = ⚠️
（预期之内，但确实变了数据，必须知悉）。

### 几何守恒怎么判才算数（重要）

**不要用「世界包围盒」判几何守恒** —— 两侧口径不对等：

| 侧 | 算法 | 性质 |
|---|---|---|
| 基线 | `obj.bound_box`（局部 AABB）乘 `matrix_world` | **松上界**（局部 AABB 经旋转必然膨胀） |
| 拆分后 | 各部件局部 AABB 变换后取**并集** | 每部件跨度更小 ⇒ 上界更紧 |

并集几何上必然 ⊆ 原上界，于是会报出「漂移」——那是**判据不等价**，不是数据变了。
实测反例：`对象9287` 的真实世界范围是 Y `0.14~7.31`，而「局部 AABB 变换」给出 `-11.28~16.31`，
两者差了一个数量级；该对象在旧判据下报 `1.557e-03` 的漂移，实际几何逐位未变。

**正确判据：两侧都取「逐顶点局部坐标的 min/max」。** 算法一致、与帧无关，应精确相等。

* `对象9287`：并集 vs 磁盘未拆分快照 `max|Δ| = 4.551e-07`
* `对象9041`：`max|Δ| = 4.141e-07`
* 该量级下 float32 的可表示间隔约 `3.05e-05` ⇒ 差值**小于一个浮点台阶**，即逐位一致。
* 脚本包已把 `local_extent` 写入基线，验证器第 7 节据此判定；世界包围盒降级为**仅供参考、不参与判定**。

## 前置条件(不满足就别拆)

| 条件 | 为什么 | 不满足怎么办 |
|---|---|---|
| 材质槽 ≥ 2 | 1 个槽拆了没意义 | —— |
| 至少有 2 个槽**有面指向** | 空槽不会生成部件；**部件数 = 「有面的」槽数**，不是槽总数 | **不需要**先清空槽 —— 拆分时会自动清除（实测） |
| 网格数据 `users == 1` | 多对象共享网格时拆分会互相干扰 | 先单用户化(`scripts/make-independent/`) |
| 对象处于 OBJECT 模式 | 算子需要在 Object 模式下切进 Edit 再切回 | 脚本会自动处理 |

## 操作方式

### 视口手动

选中对象 → `Tab` 进编辑模式 → `P`(Separate)→ `By Material`。
(注意:**不用先选面**,By Material 对整网格生效。)

### 脚本 / 桥

```python
# separate_by_material.py
MODE = "separate"; TARGET = "对象13735"
```

`python send.py separate_by_material.py` —— 自检 → 录基线 → 拆分 → 盘点,全程状态写盘。

> ⏱ **为什么必须逐阶段写盘**:桥的 `exec` 在 Blender **主线程**执行,客户端 **120s 超时**后
> 结果即丢失;主线程忙时后续请求**只排队不执行**,所以拆分期间**无法轮询进度**。
> 超时后从 `STATUS_JSON` 回捞结论。真实案例 350 万面耗时 **10.5 s**,远低于阈值,
> 但这个约束对更重的网格是硬性的。

## 验证(独立请求 + 磁盘基线)

改动前先用同一个快照函数录基线,改完**另开一次请求**读基线逐项比对:

| 判据 | 通过标准 | 真实案例实测 |

| 面数守恒 | **精确相等** | 3,505,328 → 3,505,328 ✅ |
| 顶点数守恒 | 相等 ⇒ 材质组拓扑独立 | 2,020,266 → 2,020,266 ✅ |
| 父级 / MPI / 世界矩阵 | `max|Δ|` < 1e-6 | **0.000e+00** ✅ |

| UV / 自定义拆分法线 | 保留 | 全部保留 ✅ |
| 集合归属 | 与基线相同 | 相同 ✅ |
| 材质 `users` | 全部 ≥ 1 | 1 → 1 ✅ |
| 动画 / 修改器 / 形态键 | 与基线一致 | 全部 None / 空 ✅ |
| 孤儿 mesh | 不存在 | 无 ✅ |
| 下游引用 | 明确报出 | 零引用 ✅ |
| **新增**孤儿 mesh | 与基线 `orphan_mesh_before` 差集为空 | 0 个新增;10 个历史遗留单列提示 ✅ |
| **本组**新增对象数 | == 有面材质槽数 - 1(以 `TARGET + "."` 为前缀口径) | 3 == 3 ✅ |

**顶点数为什么会增加**:若材质边界处**共享顶点**,拆开后各组会各自复制一份,
总数必然变大(合成自测 `shared` 变体:52 → 64,+12)。**这不是数据损坏**,
但要知道它发生了 —— 验证器会把它作为提示(ℹ️)而非失败(❌)报出来。

## 关键坑:属性层"消失"不等于数据丢失

拆分后常见现象:某个部件的 `sharp_edge` 属性层**不见了**,其它部件还在。

**机制**:Blender 会丢弃结果网格上**全为默认值**的属性层。
所以判定逻辑是:

| 基线该组锐边数 | 部件属性层 | 判定 |
|---|---|---|
| `0` | 不存在 | ✅ Blender 丢弃全默认值层,**无信息损失** |
| `> 0` | 不存在 | ❌ **真数据丢失** |
| 任意 | 存在且计数相等 | ✅ 保留完好 |

⇒ **基线里必须记录"每个材质组内的锐边数"(`sharp_by_mat`)**,否则这件事无法判定,
只能停留在"可能丢了也可能没丢"的猜测。真实案例的决定性证据:

| 材质槽 | 基线该组锐边数 | 拆分后部件 | 吻合 |
|---|---|---|---|
| 0 | 68,142 | `对象13735.001` 锐边 68,142 | ✅ |
| 1 | 2,461,210 | `对象13735.002` 锐边 2,461,210 | ✅ |
| 2 | 80,886 | `对象13735.003` 锐边 80,886 | ✅ |
| 3 | **0** | `对象13735`(原对象)**属性层消失** | ✅ 无损失 |

## 坑(逐条实测)

### 1. `hasattr(bpy.ops.mesh, "separate_by_material")` 是假阳性

`hasattr` 返回 `True`,你以为算子存在;真去调就 `KeyError`。
判 `bpy.ops` 算子存在性**必须用 `get_rna_type()`**。同类问题在 `bpy.ops` 上普遍存在。

### 2. 桥 120s 超时 + 主线程阻塞 ⇒ 长耗时算子必须写盘

`exec` 在主线程跑;主线程忙时新请求只排队不执行 ⇒ **算子运行期间无法轮询**。
把状态**逐阶段 `json.dump`**,超时后读磁盘回捞。

### 3. 拆分脚本里禁止写 `if __name__ == "__main__"`

桥的 `_env()` 命名空间里**没有 `__name__`** → 写了直接 `NameError`。
(同源问题:Blender 执行 `scripts/startup/*.py` 时 `__name__` 是模块名,不是 `"__main__"`。)
结尾**无条件**调用 `main()`。

### 4. 同一次 exec 内"改完立即验证"会读到未刷新缓存

数值可能不对(数据其实是对的)。验证一律**另开一次请求**,并且尽量**读磁盘基线**而不是内存快照。

### 5. `evaluated_get(dg).matrix_world` 是活引用

不 `.copy()` 直接存进列表,**循环结束后所有样本都变成最后一帧的值**。
(`to_3x3()` / `to_translation()` 返回新对象,天然安全。)

### 6. `Material.use_nodes` 已弃用

Blender 5.2 起抛 `DeprecationWarning`(预计 6.0 移除)。判"材质有无节点"用
`mat.node_tree is not None`。

### 7. Empty 不支持修改器

不能把"引用测试"的修改器挂在空对象上 —— 必须用网格对象。
(踩过一次:`ref.modifiers.new()` 在 Empty 上返回 `None`,然后 `AttributeError`。)

### 8. `VERTEX` / `VERTEX_3` 顶点父级在拆分后失去意义

顶点索引变了。`refs_scan.py` 会把这类引用单独报出来。

### 9. 编辑器选择掩码与 `material_index` 会"消失"—— 正常

* `.select_edge` / `.select_poly` / `.select_vert` / `.uv_select_*`:选择状态本就不该保留
* `material_index`:每部件只剩 1 个槽时这个属性层无意义,Blender 会去掉

验证器把这类归为"正常消失层",只把**其它载荷层**的丢失算作异常。

### 10. 原点不动,别担心"漂移"

拆分沿用原对象的局部变换与 `matrix_parent_inverse`,所以部件之间**没有相对位移**。
验证第 4 项(世界矩阵)和第 7 项(包围盒并集)就是盯这个,实测 `0.000e+00`。

### 11. 「孤儿 mesh」判据必须做基线差集,不能用绝对判无(v1.17.1)

验证器原先写的是"存在 `users=0` 的 mesh 就报错"。这在**工程本来就有历史遗留孤儿**时**必然误报**:
实测对象 `水晶走廊_纵向灯2`(4 槽)拆分后 35 项全绿,却因 10 个**拆分前就存在**的孤儿
(早期删对象留下的数据块,每个仅 26~78 面)被判"不通过"。

⇒ 正确判据是**差集**:基线记 `orphan_mesh_before`,只把 `orphan_now - orphan_before`
(本次**新增**孤儿)判 ❌;交集部分(拆分前既有)降级为 ℹ️ 提示 —— 与本次操作无关,
且 Blender 存盘时本就会按孤儿丢弃。

**推广**:凡"存在性检查"(孤儿数据块 / 空集合 / 缺贴图 / 游离引用),判据取**差集**、不取**绝对值**
—— 真实工程的状态往往不是干净的初始态。

### 11. 判据必须「取差集 + 精确到本次操作的对象集合」(v1.17.1)

验证器第 11 节踩了**同一处病根的两个实例**:

**实例①:孤儿判据用了「绝对判无」。** 原先写的是"存在 `users=0` 的 mesh 就报错"。
这在**工程本来就有历史遗留孤儿**时**必然误报** —— 实测某对象 4 槽拆分后 35 项全绿,
却因 10 个**拆分前就存在**的孤儿(早期删对象留下的数据块,每个仅 26~78 面)被判"不通过"。
⇒ 正解:**差集**。基线记 `orphan_mesh_before`,只把 `orphan_now - orphan_before`(本次**新增**)判 ❌;
交集部分(拆分前既有)降级为 ℹ️ 提示 —— 与本次操作无关,且 Blender 存盘时本就会按孤儿丢弃。

**实例②:计数判据用了「全场景口径」。** `新增对象数 == 材质槽数-1` 里的 `new_objs`
取的是 `set(D.objects) - before_objs`,是**全场景**差集。同一场景**连着拆多个对象**时必然串扰 ——
实测先拆 `水晶走廊_纵向灯`、再拆 `水晶走廊_竖向灯`,回头复验前者看到
「新增对象数 **4** != 材质槽数-1 (1)」(把后者新增的 3 个也数进去了)。
⇒ 正解:**只数本组**,即"以 `TARGET + "."` 为前缀的新增对象";全场景多出的部分仅作附注。
(`TARGET + "."` 对"名字互为前缀"的对象安全:`纵向灯` 是 `纵向灯2` 的前缀,
但 `纵向灯2.001` 不匹配 `纵向灯.`)

**推广**:凡"存在性 / 计数"检查(孤儿数据块 / 空集合 / 缺贴图 / 新增对象数),
判据都要**取差集、且精确到本次操作的对象集合** —— 真实工程状态往往不是干净的初始态,
而且操作**是连着做的**,用全场景绝对值必然误报或串扰。
